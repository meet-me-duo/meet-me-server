# Development Rules

## 브랜치 구성

- `main`: 배포 가능한 안정 상태를 유지한다.
- `develop`: 다음 배포에 포함할 기능을 통합한다.
- `develop`에서는 코드, 인프라와 프로젝트 문서를 직접 변경하거나 커밋하지 않는다. 병합과 피처 브랜치의 기준점으로만 사용한다.
- `feature/<topic>`: 최신 `develop`에서 생성하고 하나의 기능 목적만 포함한다.
- 피처 브랜치를 만들기 전에 작업 트리가 깨끗한지 확인하고 `git switch develop`, `git pull --ff-only origin develop` 순서로 원격 변경을 반드시 반영한다.
- `develop` pull이 충돌하거나 fast-forward 할 수 없으면 피처 브랜치를 만들지 않으며, 임의로 merge/rebase하지 않고 사용자에게 해결 선택지와 트레이드오프를 제시한다.
- 기능 검증이 끝나면 feature 브랜치를 `develop`에 병합하고, 배포 준비가 끝난 `develop`을 `main`에 병합한다.
- 병합을 마친 feature 브랜치는 삭제한다.

## 개발 흐름

- 구현 전에 관련 PRD, Architecture, ADR와 프로젝트 규칙을 확인한다.
- 구현에 의미 있는 제약이나 복수의 방안이 있으면 각 선택지의 장점, 단점, 비용과 장기 영향을 제시하고 사용자 선택을 받은 뒤 구현한다.
- 외부 계정, 권한, 결제, 동의 또는 비밀정보가 관련되면 `.agents/rules/user-intervention.md`에 따라 `[AGENT]`, `[USER]`, `[SHARED]` 작업으로 분리하고 사용자가 그대로 수행할 수 있는 단계별 행동을 종속 작업 전에 안내한다.
- 외부 계약과 아키텍처에 영향을 주지 않고 쉽게 되돌릴 수 있는 사소한 내부 세부사항만 합리적인 기본값으로 진행한다.
- 변경 후 영향 범위가 가장 작은 테스트부터 실행하고 결과를 확인한다.
- 프로덕션 Kotlin 코드를 변경할 때는 `src/test/kotlin` 아래의 관련 테스트를 먼저 추가하거나 함께 변경한다.
- ArchUnit·Konsist 같은 자동 아키텍처 검사는 initial commit과 Phase 1의 선행 조건 또는 공통 품질 게이트에 넣지 않는다. 그동안 코드 리뷰에서 `domain <- application <- adapter` 의존 방향과 Domain의 프레임워크 독립성을 확인한다. 기능·Adapter 증가로 수동 검토 부담이 커지거나 실제 경계 위반이 발견되면 도구의 Kotlin 호환성·검사 범위·유지 비용을 다시 비교한 뒤 선택 도입한다.
- Codex가 `git commit`을 실행하기 전 `.codex/hooks/tdd_guard.py`로 `ktlintCheck`, `assemble`, `test`를 모두 검증한다.
- 사용자와의 대화에서 작업 범위, 우선순위 또는 결정이 변경되면 `implementation_plan.md`를 현재 합의와 일치시킨다.
- 사용자가 작업 완료 후 커밋과 푸시를 요청하면 코드 커밋 전에 `implementation_plan.md`의 완료 항목, 현재 진행 요약, 최종 갱신일과 진행 기록을 먼저 갱신한다.
- 커밋 전 진행 기록에는 변경 요약과 검증 결과를 적고 Commit/PR 칸은 `동일 커밋 예정`으로 기록할 수 있다. 커밋 해시는 Git 이력을 기준으로 확인한다.
- PR 제목과 본문은 사람이 빠르게 이해하고 검토할 수 있는 자연스러운 문장으로 작성한다. `파괴적인`, `뒤집기`처럼 번역투이거나 실제 영향을 모호하게 만드는 표현은 사용하지 않고 `기존 API와 호환되지 않음`, `데이터 마이그레이션 필요`처럼 변경 결과를 구체적으로 설명한다.

## 위험도 기반 TDD

- TDD 운영 방식은 **선택지 B — 위험도 기반 역할 분리**를 사용한다.
- 일반적인 CRUD, 설정, 단순 매핑과 얇은 어댑터 변경은 같은 작업자가 테스트와 구현을 맡되 아래 Red-Green-Refactor 절차와 검증 기준을 지킨다.
- 다음 고위험 변경은 테스트 설계자와 구현자 역할을 분리한다.
  - 일정 교집합, 거리, 후보 점수, Plan A/B/C와 같은 핵심 결정론적 도메인 규칙
  - 인증·인가, 토큰, 개인정보 비공개, 로그 마스킹과 그 밖의 보안 경계
  - OAuth, Calendar, Gemini, 지도 API 등 외부 공급자 계약과 장애 처리
  - Flyway 마이그레이션, 트랜잭션, 동시성, 멱등성과 데이터 유실 가능성이 있는 영속성 변경
- 테스트 설계자는 PRD, Architecture, ADR, 합의된 Decision Gate와 공개 계약만을 근거로 테스트를 작성하며 구현 세부사항을 기대값의 근거로 사용하지 않는다.
- 구현자는 확정된 테스트를 삭제하거나 기대값을 약화하여 GREEN을 만들지 않는다. 스펙 오류나 테스트 결함을 발견하면 구현을 멈추고 테스트 설계 단계로 되돌린다.
- 사용자는 모호하거나 제품 동작을 바꾸는 기대값만 결정한다. 명확한 스펙에서 테스트를 도출하고 실행하는 작업은 `[AGENT]`가 담당한다.
- 고위험 변경의 최종 검증에는 구현과 분리된 테스트 검토와 해당 경계에 맞춘 의도적 결함 주입 검증을 포함하여 테스트가 의도적인 결함을 탐지하는지 확인한다.
- PIT는 **선택지 B — 핵심 결정론적 매칭 로직 구현 후 선택 적용**으로 운영한다. Initial commit과 Phase 1의 선행 조건이나 공통 커밋·PR 품질 게이트에는 PIT를 넣지 않는다.
- 시간 교집합, 날짜 범위, 장소 허용 영역, 후보 점수와 동률 해소처럼 순수 Domain의 핵심 계산이 구현된 뒤 기존 테스트의 결함 탐지력을 평가할 실익이 생기면 PIT 도입 비용, Kotlin 호환성과 실행 시간을 다시 비교한다. 채택할 경우에도 효과가 큰 해당 패키지에만 한정한다.
- 인증·트랜잭션·동시성·멱등성 및 외부 공급자 Adapter는 PIT 채택 여부와 무관하게 해당 경계에 맞춘 의도적 결함 주입 검증을 사용한다. PIT가 외부 장애·락 경합·네트워크 계약을 충분히 검증한다고 간주하지 않는다.
- 테스트 명명, 커버리지와 의도적 결함 주입 결과 형식은 각각의 비용과 피드백 시간을 비교해 사용자와 합의한 뒤 확정한다. PIT를 후속 채택할 때 세부 버전·대상·제외 규칙·통과 기준과 CI 실행 주기를 함께 확정한다. 라인 커버리지 단독으로 테스트 품질을 판정하지 않는다.

## Red-Green-Refactor

1. **Spec:** 작업에 관련된 요구사항 ID, 도메인 규칙, 정상·경계·실패 예시와 불변식을 테스트 목록으로 만든다. 의미 있는 해석 차이는 구현 전에 사용자에게 선택지와 트레이드오프를 제시한다.
2. **Skeleton:** 테스트를 컴파일하는 데 필요한 값 객체·데이터 클래스 껍데기, port 인터페이스와 use case 메서드 시그니처만 추가할 수 있다. 동작이 필요한 본문은 `TODO("TDD RED: <spec-id>")`로 두며 `null`, `false`, 빈 컬렉션 또는 하드코딩한 값으로 가짜 성공을 만들지 않는다.
3. **Red:** 가장 작은 대상 테스트를 실행한다. 테스트가 컴파일되고, 아직 없는 요구사항 때문에 예상한 지점에서 실패해야 한다. 문법, 설정, 의존성 또는 테스트 데이터 준비 오류는 유효한 RED가 아니다. 실행 명령, 실패 테스트와 예상 실패 이유를 RED 근거로 기록한다.
4. **Green:** 실패한 테스트를 통과시키는 최소 프로덕션 코드만 작성하고 가장 작은 대상 테스트부터 다시 실행한다.
5. **Refactor:** GREEN을 유지하면서 중복, 이름, 책임과 의존성 방향을 개선한다. 기대 동작을 바꾸거나 새 사례를 추가하면 새 TDD 주기로 취급한다.
6. **Verify:** 관련 단위·계약·통합·아키텍처 테스트를 작은 범위부터 실행하고 마지막에 `ktlintCheck`, `assemble`, `test`를 실행한다. 고위험 변경은 별도의 테스트 검토와 합의된 결함 주입 검증도 통과해야 한다.

- RED 확인 후 테스트의 입력, 기대값 또는 검증 논리를 바꾸면 기존 RED 근거는 무효다. 변경된 테스트로 RED를 다시 확인한다.
- 테스트는 공개된 도메인 동작, port/use case 계약 또는 adapter 계약을 검증하며 private 메서드와 우연한 내부 호출 순서에 결합하지 않는다.
- 각 테스트 또는 테스트 묶음은 가능한 경우 PRD 요구사항, 도메인 규칙이나 Decision Gate 식별자를 추적할 수 있어야 한다.
- 정상 사례만으로 완료하지 않고 관련 경계값, 거부 조건과 도메인 불변식을 포함한다.
- 최종 프로덕션 코드에는 RED용 `TODO("TDD RED: ...")`가 남아 있어서는 안 된다.

## TDD 가드 강화 설계

- 현재 `.codex/hooks/tdd_guard.py`의 테스트 변경 확인과 최종 품질 게이트는 유지한다.
- RED 증거는 **선택지 C — Git 추적 요약과 로컬 원본 로그 분리** 방식으로 관리한다.
- Git에는 `.tdd/red/<work-item>.json`의 간결한 증거 요약을 추적한다. 요약에는 작업 식별자, 기준 source revision, 테스트 파일 경로와 SHA-256 지문, 실행 명령, 실패 테스트, 예상 실패 분류와 기록 시각만 포함하고 전체 테스트 출력이나 사용자·비밀정보를 넣지 않는다.
- 전체 RED 실행 출력은 `.codex/tdd-evidence/<work-item>.log`에 로컬 전용으로 저장하고 Git에서 제외한다. 로컬 commit guard는 요약과 원본 로그를 함께 검증하되 CI와 코드 리뷰는 Git에 추적된 요약, 테스트 지문과 변경 이력을 검증한다.
- 프로덕션 Kotlin 변경이 있으면 유효한 RED 근거가 있는지 검사하고, RED 이후 테스트 지문이 바뀌었으면 커밋을 차단하여 RED 재확인을 요구한다.
- 커밋 전 `src/main/kotlin`의 RED용 `TODO` 잔존 여부를 검사한다.
- 고위험 변경은 역할이 분리된 테스트 검토 결과와 의도적 결함 주입 결과를 커밋 또는 CI 품질 게이트에 연결한다. PIT는 핵심 결정론적 매칭 로직 구현 후 별도로 채택한 경우에만 해당 범위의 게이트에 연결한다.
- RED 요약 JSON Schema, 파일 수명주기와 가드 구현은 위 경계를 따른다. 의도적 결함 주입 결과 형식은 구현 전에 선택지와 트레이드오프를 비교하여 별도로 확정한다.

## 변경 단위

- 하나의 변경에는 하나의 명확한 목적을 유지한다.
- 공개 API가 변경되면 Swagger/OpenAPI 문서와 관련 테스트를 함께 변경한다.
- 아키텍처에 장기 영향을 주는 결정만 ADR 후보로 분류한다.
- PR 본문은 변경 목적, 변경 내용, 실행한 검증, 리뷰 요청 사항, 영향 범위와 관련 이슈를 중심으로 작성하고 모든 PR에 일률적인 체크리스트 작성을 요구하지 않는다.
