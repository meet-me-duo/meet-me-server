## 공통 기준 제안

1. **명시적 유연성 보존**: 본인이 허용한 넓은 범위·선호·제외·대안과 유효한 다른 참가자 가용성 의존은 그대로 보존한다. 단일 날짜/시간으로 축소할 수 있는지를 CLEAR 기준으로 삼지 않는다.
2. **필수 사실의 미확정**: 본인 조건의 허용 여부를 결정하는 필수 개인/현장 사실이 원문·제공 문맥에 없고 그 사실의 가능한 값에 따라 허용 일정이 달라지면 보완 대상이다. 일상 시각을 추측하지 않는다. 빠진 숫자가 있다는 이유만으로 모든 상대 조건을 모호하다고 취급하지 않는다.
3. **조건 적용 대상 미확정**: 시간·날짜·장소·방식·부정·예외가 어느 대상에 붙는지에 따라 허용 일정이 달라지면 그 결속만 확인한다. 이미 문맥으로 해소된 날짜나 의도된 대안은 재질문하지 않는다.
4. **앱 표현 한계 분리**: 의미와 허용 범위가 이미 정해졌다면 현재 구조화 스키마 미지원·후보0·검색기간 밖이라는 이유만으로 모호성으로 바꾸지 않는다. 기존 최종 전체 분석의 미반영 처리는 별도다.

여기서 ‘허용 일정’은 날짜/시각뿐 아니라 장소·방식·명시된 조건 관계를 포함한다. 타인 가용성에 맞추겠다는 명시적 관계는 최종 전체 입력에서 평가할 수 있는 허용 조건이다. 반면 숨은 개인 퇴근시각은 관계 문구를 그대로 보존하는 것만으로 본인의 필수 경계가 정해지지 않는다. 후자의 구분을 A instructions·choice 설명·B instructions·평가 정의에 같은 문장으로 명시하는 것이 제안 범위다. 이를 최종 매칭 성공이나 모든 조건의 현 스키마 지원 보장으로 확대하지 않는다.

## 최소 질문과 현재 API 경계

표의 ‘최소 확인’은 필요한 사실의 명세이며 그 질문 문장을 새 API 필드로 내보낸다는 뜻이 아니다. 현재 B는 NEEDS_CHOICE에서만 prompt/sourceExcerpt/정확히A·B complete proposals를 제공하며, NEEDS_EDIT에는 질문·reason 필드가 없다. 안전한 두 complete 해석을 원문/context만으로 만들 수 없으면 NEEDS_EDIT와 기존 일반 직접 수정 경로를 사용한다. ‘퇴근17시/20시 중 선택’처럼 개인 시각을 발명하지 않는다. 개별 사유가 담긴 직접 수정 안내가 필요하다면 API/UI의 별도 변경 결정이 필요하며 이번 검토안의 자동 범위에 넣지 않는다.

## 제안되는 후속 변경 범위와 검증

아직 바뀐 코드/프롬프트/정답/threshold는0이다. 후속 방향이 승인되면 첫 범위는 A의 짧은 choice 설명과 본문, B 본문, 공개 평가정의의 판단 경계를 일치시키는 최소 문구 변경이다. type=choice3·6문맥필드·모델·500자·최종분석/AREA·참여/마감·인증/소유권/revision·DB/API/UI·질문/검사/비용 상한은 변경 제안에 포함하지 않는다. 운영 confidence/가격/활성화도 별도다.

확정할 기준은 (a) 필수 개인 사실을 추측해야 하는 경우와 유효한 명시적 관계의 구별, (b) 기준점·수단 등 조건 결속의 미확정이 실제 허용 집합을 바꾸는지, (c) 스키마 미지원만으로 질문하지 않는다는 경계다. 위 마지막 이동시간 행처럼 실제로 추가 해석이 필요한 경계는 합격 예시로 미리 확정하지 않는다.

향후 무과금 검증은 원문/context wire 불변과 판정/질문 처리·실패 분리를 확인하고, 의미 효능과 분리한다. 새 의미 검증은 필요한 경우 별도 사전 고정 평가규칙/독립 새 gold/negative 대조군/호출·비용·중단 계획을 마련한 뒤 진행한다. 기존 B2는 관측 후 노출된 개발 진단이고 기존 gold를 바꾸거나 fresh로 재사용하지 않는다. confidence 임계값을 이 표본에 맞춰 낮추지 않는다. 이번 단계에서 추가 유료 호출·prompt patch·운영 활성화는 하지 않는다.
