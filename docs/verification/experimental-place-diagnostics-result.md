# 이동 제약 미지원 진단 보존 — 격리 무료 검증 (2026-10-30)

> 공개용 역사 기록: 아래 수치와 실행 제한은 해당 실험 당시의 결과다. 원본 응답·로그·개인정보·내부 대화 식별자는 게시하지 않는다. 현재 통합 소스의 검사 상태는 [게시 준비 요약](issue-176-publication-readiness.md)을 따른다.

> 후속 마무리: 무료 settings 공유 상태를 분리한 뒤 최종 전체 **2593PASS/0FAIL/기존17SKIP**, ktlint·assemble PASS를 확인했다. 아래 마지막1FAIL 수치는 이전 체크포인트의 기록이다. [최신 원인·전체 검증 결과](experimental-place-regression-closure-result.md)를 기준으로 한다.

이번 변경은 처리하지 못한 이동 조건을 성공·충돌로 오인하게 하는 진단 누락을 수정한다. 특정 지명이나 pilot을 통과시키는 예외는 없다. 실제 도보 시간 검증이나 대면 가능 조건을 새로 도입하지 않았으므로 원래 IN_PERSON 사례의 추천 성공을 뜻하지 않는다.

## 구현과 호환 경계

- `PlaceConstraintDiagnostics`는 동결된 구조화 조건에 TravelConstraint가 있는지로 미지원 사유를 도출한다. 문자열 내용·지명·분 수·테스트 ID를 판정에 사용하지 않는다.
- 새 처리에서 미지원 이동 조건은 PARTIAL로 표시하며, 기존 주최자 전용 미반영 API에 `UNSUPPORTED_TRAVEL_CONSTRAINT`/`PLACE`를 반환한다. 원문과 최종 보완 답변은 기존 공개 범위로 제공하며 중간 질문은 추가하지 않는다.
- 일부 장소 조건이 미반영된 제출 ID는 한 번만 집계한다. `applied_submissions`는 완전 반영 제출 수이므로 그 수와 추천에 기여한 시간/참석자 수를 동일하게 해석하면 안 된다.
- 모델 rejection→기존 장소 실패→새 이동 미지원 사유 순서를 유지한다. 유효 시간, 필수 장소와 선호, 실제 영역 교집합·후보 계산·확정 저장·권한 검증은 유지한다.
- 원래 structured 조건과 frozen 원문/보완을 재작성하지 않는다. 기존 저장 자료로 진단을 도출하므로 새 DB 열/migration·공급자 prompt/schema·API 응답 필드 변경은 없다. API 사유 설명과 웹의 사유 문구만 보완한다. CSS/레이아웃은 변경하지 않는다.
- 과거 완료·확정 결과 불변 계약에 따라 새 이동 진단의 조회 집계는 저장 품질 PARTIAL에서만 추가한다. 과거 COMPLETE 결과의 품질·집계·후보·선택을 조회나 재처리로 바꾸지 않는다. 과거 COMPLETE의 진단까지 소급 해결한 것으로 주장하지 않는다.

## 확인한 일반 의미와 남은 지원 정책

공통 AREA는 대표 지역 호환성이고 실제 보행 시간 충족의 증거가 아니다. 서로 다른 지원 영역의 교집합 부재는 정상적인 장소 불일치이며 파싱 실패로 바꾸지 않는다. 계산하지 못한 TravelConstraint는 실제 모순이라고 단정하지 않는다. 개인 기준점이 미상인 표현과 명시 장소+도보 제한은 원래 서로 다른 구조화 정보 그대로 보존한다. 현재 문자열 이동 제약에 기준점·이동수단·상한을 안전하게 연결하는 계약은 없어 이번 수정에서 추정하지 않는다.

독립 정상/경계 축은 공통 영역, 서로 다른 영역, 개인 기준점 미상, 명시 기준점+복수 제한, 같은 기준점의 상이한 제한, 시간 불가 차감, 필수/선호 구분, REMOTE/EITHER/IN_PERSON, 중복 없는 집계, 거절 우선순위, 주최자 권한, 과거 완료·확정 불변이다. 이번 pilot은 이미 알려진 개발 사례이며 블라인드 일반화 성능의 증거가 아니다. 봉인 사례는 개봉하거나 수정하지 않았다.

추가 대면 지원은 별도 선택이 필요하다. 보수적으로는 계산 불가인 강한 이동 조건을 현재처럼 대면 후보에서 배제하고 사유를 보인다. 대표 지역 후보를 미검증 조건과 함께 허용하려면 조건별 상태와 후보의 의미·고지·확정 계약을 먼저 합의해야 하며, 도보 제한 충족으로 표시해서는 안 된다. 정확한 이동시간 검증은 지도/경로 기능의 별도 범위다. 이번에는 어느 새 정책도 확정하지 않았다. 선호만 있는 표현을 필수 허용 장소로 바꾸는 것도 별도 의미 판단이며 이번 사례의 정답에 맞춰 바꾸지 않는다.

후속 설계에서는 하나의 nullable `offlineArea`로 합쳐진 상태를 먼저 분리하는 것이 안전하다. 후보 계산이 지원하는 명시 영역, 개인 장소 필수 조건 없음, 미확정 장소, 계산 불가 이동 조건, 실제 영역 교집합 없음은 서로 다른 상태다. 특히 필수 장소 조건이 없는 참여자를 무제약으로 취급하는 것은 선호를 필수 조건으로 승격하는 것과 다르다. 현 구현을 그 방향으로 바꾸는 경우에도 전체 무제약 모임의 대표 장소, 강한 이동 조건의 제외 경계, 시간·장소 결합을 사전에 정해야 하므로 이번에는 매칭 상태를 바꾸지 않는다. 기준점·이동 수단·제한 값을 연결하는 구조화 계약을 확장한다면 기존 opaque 문자열은 검증되지 않은 상태로 복원하고, 새 독립 계약/봉인 평가를 선행해야 한다.

## 최종 검증 결과와 남은 범위
