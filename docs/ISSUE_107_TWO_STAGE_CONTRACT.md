# #107 2단계 검사 개발 계약 TS01–TS12

2026-10-18 UTC. 사용자 승인: 충분히 확신한 Decisions CLEAR는 통과하고 모호성 의심·정상 낮은 확신은 생성 LLM이 재확인한다. 생성 단계는 CLEAR 또는 기존 NEEDS_CHOICE/NEEDS_EDIT를 반환할 수 있다. 실제 품질·비용·키·운영 활성화 승인은 별개다.

- TS01: `TwoStagePreSubmissionCheckProvider`는 기존 PreSubmissionCheckProvider를 구현한다. 새 classifier port와 기존 생성 provider를 조합하며 worker의 원문 보존·ownership/revision/generation·deadline/마감 게시 권한은 그대로 둔다. 최종 마감 전체 분석·AREA·matching·선택/직접수정의 재검사도 유지한다.
- TS02: 충분한 classifier CLEAR만 Precheck CLEAR 후보로 반환한다. NEEDS_REVIEW, 정상 MODEL_UNCERTAIN/LOW_CONFIDENCE의 INDETERMINATE는 생성 단계로 보낸다. REFUSED·API/설정/timeout/invalid response는 별도 실패이며 CLEAR나 자동 생성 전환이 아니다. CLEAR/NEEDS_REVIEW에 reason이 있거나 confidence가 누락/비유한/범위 밖인 모순 결과, INDETERMINATE의 reason 누락도 실패다. 정상 LOW_CONFIDENCE/MODEL_UNCERTAIN 유보의 confidence도 유한0..1이어야 하며 누락이면 실패다. REFUSED는 confidence 부재를 정상 거부 형태로 처리하지만 생성/통과로 보내지 않는다. bridge는 adapter confidence 임계값을 중복 운영하지 않고 typed result의 일관성을 검증한다.
- TS03: 생성 단계는 정확히 보존된 원문/context/anchor를 받으며 CLEAR 재판정·기존 안전한 질문·직접 수정을 사용할 수 있다. 자유 구간/질문 생성은 기존 생성 provider의 검증 계약 안에서만 가능하다. 분류기에는 구간/질문 생성을 요청하지 않는다. 첫 단계 정상 유보의 추가 생성도 예산 예약 없이는 허용하지 않는다.
- TS04: 한 provider 요청 전체에 min(request.timeout,15초)의 하나의 monotonic deadline을 고정한다. 2차에는 남은 시간만 전달하고 stage별 새 15초를 지급하지 않는다. reserve/usage 기록 시간까지 전체 deadline에 포함하고 호출 전/후 deadline을 검사하며 오래된 결과는 실패다. 브라우저/queue30초와 게시 예약3초는 기존 worker가 유지한다.
- TS05: 기존 PrecheckProviderRequest에 optional roomId·executionGeneration을 추가해 실제 worker가 고정된 room/check/generation을 전달한다. 분류 payload에는 식별자를 보내지 않으며, 새 roomId·executionGeneration은 두 adapter의 외부 payload에 보내지 않는다. 기존 Gemini의 불투명 input_ref(checkId) wire는 유지한다. 새 2단계는 누락 room/generation을 호출 전 거부한다. 기존 생성 provider 직접 사용·역사 테스트의 기본값은 유지한다.
- TS06: 공통 `AiCallBudgetPort`가 물리 요청 상한과 검증된 quote를 포함하는 reservation을 **외부 단계 전에** 부여해야 한다. request는 roomId, opaque execution/check+generation+stage 멱등키, purpose, source/context/profile fingerprint, 최대 물리 호출수다. classifier는1, 기존 생성 adapter의 count+generation bundle은최대2를 보수적으로 예약한다. bundle 일부가 실행되지 않았다고 자동 환급하지 않는다. 돈/호출수를 나눠 실제 count/gen을 혼동하지 않는다.
- TS07: 기본 budget 구현은 DENY다. 금액·가격/청구 상한·예산 소진 정책은 이 계약에서 정하지 않는다. 현재 profile fingerprint는 단계/프로토콜/출력 제한의 안정적 해시이며 모델·threshold·실제 가격/quote 검증을 결속한 운영 profile이 아니다. 미승인/미입증 quote·중복 reservation·budget unavailable/denied이면 해당 단계 outbound0이고 실패한다. 새로운 승인 UI/권한 체계를 만들지 않는다. 합성 테스트만 fake 승인 quote·모임 누적 ledger를 사용한다.
- TS08: 호출을 시작한 뒤 timeout/API 오류/거부/usage 미수신/비용 불명/crash는 UNKNOWN 예약을 보존한다. free/0 refund로 settle하지 않는다. 정상 응답의 알려진 usage도 실제 billed upper bound 증거와 분리하며 budget port에 partial/unknown을 전달한다. budget 기록에는 각 stage의 provider/model/input/output/usageComplete/billedCostKnown을 따로 전달한다. 기존 단일 provider/model의 PrecheckProviderResult에는 terminal stage metadata만 반환한다. A 단독 CLEAR의 outputTokens는 기존 생성 결과 cap의 적용 대상이 아니므로 null(N/A)로 반환하며, 실제 알려진 Decisions output usage는 A의 budget observation·metrics에 보존한다. B의 terminal output usage와 기존 worker의 음수/2048 cap은 유지한다. A+B 합계를 B모델의 청구량으로 표시하지 않는다. 모임 전체 합계는 완전한 stage ledger 없이 주장하지 않는다. 기존 생성 adapter의 count 청구 usage가 없으므로 generation bundle observation의 usageComplete는 false로 유지하고 terminal known token만 보존한다. 형식 실패 전에 읽은 classifier의 known usage는 안전한 metrics에 남을 수 있으나 failureCode 전용 exception을 거치면 bridge budget에는 unknown으로 남는다. 모든 실패의 known usage가 ledger에 전달된다고 주장하지 않으며, durable ledger에는 안전한 typed failure usage 전파가 필요하다. 반환 결과가 제품적으로 stale여도 비용 기록은 버리지 않는다. 예산 기록 실패 시 성공을 반환하지 않는다.
- TS09: 순차/동시 호출과 generation retry는 같은 room quota를 소비해야 한다. request id 재사용은 fingerprint가 같아도 자동 재전송 권한이 아니다. source 변경·retry·stage2·최종 분석·fallback·HOST 실패 재시도·correction/DLQ 모두 같은 room ledger가 필요하다. 합성 계약 검증은 실제 PostgreSQL의 원자성/운영 최대 비용 증명이 아니다.
- TS10: 현재 구현 단계는 shared budget port·default DENY·2단계의 reservation 계약과 fake 검증이다. **영구 PG ledger와 모든 최종 분석 dispatch 연결은 예산 설계의 별도 실행 항목이며 완료로 표시하지 않는다.** 기존 최종 분석은 기존 회차별4+1이며 HOST 실패 재시도의 room 누적 상한이 아직 없다. 따라서 runtime 2단계에는 기본 DENY를 적용해 활성화하지 않는다. 이 제한을 해제하려면 실제 금액 정책/quote 입증과 전체 purpose의 durable 구현/회귀를 먼저 완료해야 한다.
- TS11: production selector는 `meetme.precheck.decision-routing.enabled=false` 기본이다. 기존 provider enabled도 false를 유지한다. selector가 꺼져 있으면 기존 Gemini provider bean과 wire가 그대로다. selector만 켜거나 키만 존재해도 default DENY로 outbound0이다. 테스트에서만 fake budget·mock classifier/generator를 명시 주입한다. 실제 key 읽기·SSM/runtime 변경을 실행하지 않는다.
- TS12: 독립 테스트는 CLEAR→generation0, suspect/정상 유보→generation1 및 재CLEAR, refusal/API 오류→generation0, 복수 모호성 NEEDS_CHOICE/EDIT 보존, 동일 raw/context/anchor, shared15초·deadline 후 CLEAR0, 각 stage reserve 전 outbound0, count/gen bundle2·두 stage같은 room·retry누적, timeout/unknown0환급·중복/동시요청, default OFF/selector만ON deny와 기존 worker 마지막CLEAR/마감/fencing 회귀를 검증한다. 외부 호출은 mock/loopback뿐이다.
