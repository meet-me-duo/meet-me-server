# PRD: AI 기반 스마트 일정 조율 에이전트

> **문서 상태:** Draft  
> **주요 독자:** 제품 기획자, 백엔드 개발자, 프론트엔드 연동 담당자, AI 코딩 에이전트  
> **문서 목적:** Wanted AI Champion 제출 MVP와 이후 확장 제품의 경험 및 핵심 비즈니스 규칙을 정의한다.

## 1. 목표

Google Calendar에서 수집한 불가 시간과 사용자가 자연어로 입력한 시간·장소 조건을 바탕으로 최적의 모임 후보를 제안하여 일정 조율 과정의 반복 입력과 사회적 마찰을 줄인다.

### 제품 한 줄 소개

> "구글 캘린더 연동하고 조건만 말해, 결정은 내가 할게"

### 비전

- 시간과 장소를 조율하며 발생하는 눈치 게임과 반복 노동을 최소화한다.
- AI는 비정형 입력의 구조화에만 사용하고, 최종 매칭은 결정론적 알고리즘으로 수행한다.
- 장기적으로 모임 1건당 AI 비용을 1원 미만으로 낮추면서 신뢰할 수 있는 스케줄 매칭을 제공한다.

### 초기 타깃

- 대학생 조별과제 팀장과 팀원
- 사이드 프로젝트 리더와 참여자

### 저장소 범위

- 이 저장소는 백엔드 서버만 구현한다.
- 프론트엔드는 별도 저장소에서 개발한다.
- 이 문서의 프론트엔드 동작은 백엔드가 제공해야 할 API 계약과 전체 제품 흐름을 설명하기 위한 요구사항이며, 이 저장소의 구현 범위에는 포함되지 않는다.

## 2. 문제 정의

1. **수동 입력의 피로:** 표를 직접 색칠하거나 시간 슬롯을 반복 선택해야 한다.
2. **복합 조건 표현의 한계:** "학교 앞에서는 화·목", "비대면이면 심야 가능"과 같은 조건부 선호를 기존 도구에 입력하기 어렵다.
3. **사회적 마찰:** 다른 사람의 가능 시간을 볼 수 있으면 사용자가 자신의 일정을 방어적으로 입력하거나 눈치를 보게 된다.
4. **최종 결정의 방치:** 공통 시간을 찾은 뒤에도 주최자가 시간과 장소를 다시 비교하고 확정해야 한다.

## 3. 제품 원칙

### 3.1 선택 가능한 기본 일정 연동 (Post-MVP)

meet-me에 로그인한 개인만 자신의 Google Calendar를 계정에 연결하고 불가 시간을 가져올 수 있다. Calendar를 계정에 연결하고 일정을 불러온 상태와 현재 참여 중인 방의 매칭에 이를 적용하는 상태는 분리한다. 주최자가 대신 정하는 것이 아니라 Calendar를 연결한 참여자 본인이 현재 방에서 사용을 ON/OFF하고, ON일 때만 자신의 Calendar 불가 시간을 매칭에 반영한다. 비로그인 게스트와 Calendar를 OFF한 로그인 사용자는 필요할 때 방 전용 격자에서 가능한 시간을 직접 선택할 수 있다. 격자는 자연어 중심 흐름을 보완하는 부가 기능이며, 선택하지 않았다는 사실 자체를 `가능 시간 없음`으로 해석하지 않는다.

Calendar를 사용하는 참여자는 필요하면 별도의 추가 불가 시간 격자로 절대 참여할 수 없는 시간을 보완할 수 있다. 방 전용 가능 시간과 추가 불가 시간은 정형 입력이며 LLM 처리 대상이 아니고 다른 방이나 계정에 재사용하지 않는다.

제출 MVP에서는 Calendar 입력 모드를 제공하지 않고 모든 사용자가 자연어 또는 방 전용 가능 시간 격자를 사용한다.

### 3.2 블라인드 입력

후보가 생성되기 전까지 참여자는 다른 참여자의 가능 시간과 개별 조건을 열람할 수 없다. 후보 생성 후에도 정상 반영된 조건은 비공개로 유지한다. 단, 사전 고지를 전제로 후보에 반영하지 못한 원문만 부분 결과와 함께 주최자에게 공개할 수 있다.

### 3.3 AI와 알고리즘의 역할 분리

- AI는 자연어 조건의 구조화만 담당한다.
- 시간 교집합, 거리 판정, 후보 순위 계산은 서버의 결정론적 알고리즘이 담당한다.
- AI가 최종 시간이나 장소를 임의로 선택하거나 계산 결과를 변경하지 않는다.

### 3.4 선택 가능한 세 가지 결과

히트맵이나 원시 시간표 대신 우선순위가 계산된 Plan A, B, C 후보를 카드 형태로 제공하고, 주최자가 하나를 선택해 확정한다.

- 후보 탐색 날짜 범위는 자연어 시간 조건을 실제 날짜별 구간으로 펼치고 Calendar 불가 시간을 검증하는 근거 기간이다.
- 결과 카드는 서버가 계산한 구조화된 가능 구간과 이를 요약한 자연어 문구를 함께 제공한다.
- 자연어 요약은 반복 일정 등록 규칙이 아니다. 예를 들어 `평일 18:00~21:00`은 탐색 범위에서 공통으로 가능한 시간대를 묶어 표현한 것이며 실제 모임 날짜는 주최자가 정해 공지한다.
- 특정 참여자의 Calendar에서 불가능한 날짜·시간은 공통 후보에서 제외한다. 요약이 여러 날짜를 묶어 표현한다면 제외 날짜나 축소된 시간대를 함께 드러내어 구조화된 후보와 의미가 달라지지 않아야 한다.
- 반복 요일·시간 조건이 있으면 서버는 탐색 범위의 실제 가능 날짜를 모두 나열하는 표현과 원래 패턴에 모든 제외·축소 예외를 붙이는 표현을 비교한다. 예외 날짜 참조 수가 실제 가능 날짜 참조 수보다 적을 때만 패턴과 예외를 사용하고, 같거나 많으면 실제 가능 날짜를 나열한다.
- Plan A, B, C는 종류별로 최대 한 장의 카드로 제공하고 각 카드 안에 해당 조건을 만족하는 모든 실제 시간 구간을 담는다. 정상적으로 계산을 마쳤지만 최소 2명이 참석할 후보가 없으면 빈 후보 목록과 `NO_MATCH` 상태를 제공한다.

### 3.5 시간대와 국제화

- MVP의 사용자 선택 시간대와 지원 언어는 각각 `Asia/Seoul`, `ko-KR`로 고정한다.
- 방과 일정 데이터는 IANA Time Zone ID와 UTC 기준 시점을 함께 사용하여 향후 방별 시간대 선택과 DST 계산을 지원할 수 있어야 한다.
- 사용자 노출 문구와 오류 메시지는 i18n 리소스로 분리하고, 도메인 상태·API 오류 코드는 언어에 의존하지 않아야 한다.
- 시간대와 언어는 별개의 설정으로 취급한다.

## 4. MVP 범위

이 문서에서 **제출 MVP**는 Wanted AI Champion 심사·투표를 위해 2026-09-21부터 로그인 없이 체험할 수
있는 공개 버전을 뜻한다. Google·Kakao 로그인과 Google Calendar 연동은 제품 목표에는 유지하되 제출 MVP
이후에 구현한다.

### 4.1 포함 사항

- 모임 목적과 선호 방식에 기반한 방 생성
- 선택적인 예상 참여 인원·제출 마감 또는 명시적인 수동 마감 방식에 기반한 조율 종료
- 로그인 없이 방을 만들고 참여할 수 있는 한시적 공개 모드
- 방을 만든 브라우저의 익명 세션에만 부여되는 주최자 권한
- 참여 링크 생성과 공유
- `Asia/Seoul` 방 시간대와 `ko-KR` 기본 locale
- 참여자의 방 전용 가능 시간 격자 입력
- 자연어 기반 시간·장소 조건 입력
- 자연어에서 특정 가능한 장소, 이동 제약과 미확정 장소를 분리
- 특정 가능한 장소의 허용 영역을 이용한 결정론적 장소 교집합 계산
- 참여자별 조건 비공개 처리
- 결정론적 시간·장소 교집합 계산
- Plan A, B, C 후보 제안
- 주최자의 후보 플랜 확정과 결과 공유
- 공개 익명 API의 호출 제한과 30일이 지난 방·게스트 데이터 정리

### 4.2 MVP 제외 사항

- 에브리타임 시간표 캡처본 업로드와 OCR을 통한 수업 시간 추출
- 확정 결과를 외부 캘린더에 쓰거나 캘린더 초대장을 자동 발송하는 기능
- 방 내부 채팅, 댓글, 투표 기능
- 매주 반복되는 일정이나 장기 팀 스케줄 관리
- 유료 결제와 구독 기능
- 공개 모임 검색이나 커뮤니티 기능
- 시스템이 주최자 대신 후보 플랜이나 실제 모임 날짜를 자동 확정하는 기능
- 운영자용 고급 분석 대시보드
- 이메일·비밀번호 기반 자체 회원가입과 로그인
- Google 및 Kakao 소셜 로그인과 서비스 Access/Refresh Token
- Google Calendar OAuth, 불가 시간 수집과 방별 Calendar ON/OFF

## 5. 사용자 여정

### 단계 1. 방 생성 — 주최자

1. 제출 MVP에서는 로그인 없이 주최자 표시 이름, 모임 목적과 선호 방식을 입력한다. 표시 이름은
   공백을 제거한 뒤 1자 이상 50자 이하이며, 서버가 발급한 브라우저 단위
   익명 자격 증명이 방 생성자와 주최자 권한을 식별한다. 소셜 로그인은 MVP 이후에 추가한다.
2. 대면, 비대면 또는 둘 다 가능한지 선호 방식을 선택한다.
3. 후보를 찾을 시작일과 종료일을 선택할 수 있다. 선택하지 않으면 화면에 표시된 기본값인 방 생성일로부터 14일을 적용한다.
4. 예상 참여 인원과 제출 마감을 선택적으로 정한다. 둘 다 정하지 않으면 수동 마감 방식을 명시적으로 선택한다.
5. 주최자는 방 생성과 동시에 첫 번째 참여자로 등록되며 예상 참여 인원에 포함된다.
6. 장소는 방 생성 시 미리 확정하지 않는다.
7. 생성된 참여 링크를 조원에게 공유한다.

### 단계 2. 조건 입력 — 참여자

1. 참여자는 1자 이상 50자 이하의 표시 이름을 입력하고 서비스 로그인 없이 공유 링크로 참여할 수 있다. 서버가 발급하여 `Secure HttpOnly` 쿠키로 전달한 브라우저 단위 불투명 게스트 자격 증명으로 자신의 참여와 제출을 식별한다. 하나의 게스트 브라우저 세션은 여러 방에 참여할 수 있지만 같은 방에서는 하나의 참여자만 소유한다.
2. 제출 MVP의 모든 참여자는 해당 방에서만 사용하는 meet-me 격자에서 가능한 시간을 선택할 수 있다.
   이 부가 입력은 계정 프로필이나 다른 방에 누적·재사용되지 않으며 화면의 주 입력으로 강조하지 않는다.
3. Google Calendar 연결·방별 ON/OFF·불가 시간 스냅샷은 MVP 이후에 제공한다.
4. 주최자가 날짜 범위를 명시한 방의 시간 격자는 가로축을 실제 날짜로 사용한다. 날짜 범위를 생략한 방은 월요일부터 일요일까지 7개 요일을 가로축으로 사용하고 선택한 가능 시간을 매주 반복되는 조건으로 취급한다.
5. "화·목 저녁에 집 근처 가능"과 같은 자연어 조건을 입력할 수 있다. 방 전용 가능 시간 격자를 하나 이상 선택했다면 자연어 없이도 제출할 수 있다.
6. 프론트엔드는 장소 전용 입력란, 지도 선택 또는 기준 좌표 수집을 요구하지 않는다.
7. 서버는 자연어 속 위치 표현을 특정 가능한 장소, 이동 제약 또는 미확정 장소로 구조화한다.
8. `봉천역`, `서울대입구역`처럼 지도 공급자가 하나의 위치로 검증할 수 있는 표현만 장소 허용 영역을 만든다.
9. `집`, `회사`, `학교 근처`처럼 개인 기준점 없이는 특정할 수 없는 표현은 장소가 아니라 이동 제약으로 처리한다. `중앙역`처럼 검색 결과를 하나로 특정할 수 없는 표현도 장소로 처리하지 않는다.
10. 사용자는 이를 보완하기 위한 별도 장소나 좌표를 추가 입력하지 않으며, 제출 시 선택한 자연어와 수동 가능 시간을 하나의 Payload로 전송한다. 공백이 아닌 자연어 또는 하나 이상의 수동 가능 시간이 있어야 제출할 수 있다. 둘 다 없으면 아직 작성하지 않은 상태이며 제출 완료 인원에 포함하지 않는다.
11. 입력 수집이 열려 있는 동안 자신의 조건을 자유롭게 수정할 수 있으며, 화면은 현재 수정 가능 여부를 명확히 표시한다.
12. 새로고침하거나 분석이 지연된 뒤에도 본인 증명 수단으로 서버에 저장된 자신의 최신 입력을 다시 조회하여 입력 화면을 복원할 수 있다.

### 단계 3. 조율과 최종 확정 — 주최자

1. 주최자를 포함한 예상 참여 인원의 제출 접수 완료, 제출 마감 도달 또는 주최자의 수동 마감 중 가장 먼저 발생한 조건으로 입력 수집을 종료한다.
2. 자동 종료 조건을 아직 충족하지 않았더라도 주최자는 경고와 재확인을 거쳐 수동으로 마감할 수 있다.
3. 제출 접수 완료는 원본 입력이 PostgreSQL에 저장된 시점이며 이때 참가자별 LLM 작업을 만들거나 구조화를 기다리지 않는다.
4. 입력 수집이 종료되면 서버는 종료 시점의 참가자별 최신 입력을 하나의 방 전체 제출 배치로 고정한다. 자연어가 하나 이상 있으면 자연어가 있는 항목만 묶어 하나의 비동기 Gemini 구조화 작업을 수행하고, 전원이 정형 일정 입력만 제출했다면 Gemini를 호출하지 않고 결정론적 매칭으로 진행한다.
5. Gemini 기술적 재시도가 모두 실패하면 서버는 입력을 보존한 채 방을 `ANALYSIS_DELAYED`로 전이하고 후보를 만들지 않는다. 프론트엔드는 로딩을 끝내고 입력이 저장되었으며 분석이 지연되었음을 안내한다.
6. 주최자는 참여자의 재입력 없이 고정된 방 전체 배치의 분석을 다시 요청할 수 있다.
7. 방 전체 배치의 구조화가 성공적으로 종결되면 서버가 유효한 조건과 일정 입력 모드별 정형 시간 구간을 이용해 결정론적 교집합 계산을 시작한다.
8. 서버는 우선순위에 따라 Plan A, B, C 후보를 생성한다.
9. 주최자는 제안된 후보 중 하나를 원클릭으로 확정한다.
10. 확정 결과를 참여자에게 공유한다.

## 6. 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| FR-000A | 제출 MVP에서는 소셜 로그인 없이 방 생성·참여·핵심 조율을 이용할 수 있어야 한다. 방을 만든 브라우저의 `Secure HttpOnly` 익명 세션만 주최자 전용 명령을 수행할 수 있어야 하며, 공유 링크만으로 주최자 권한을 얻을 수 없어야 한다. Google·Kakao 로그인과 Google Calendar 엔드포인트는 제출 MVP에서 제공하지 않는다. |
| FR-001 | 주최자는 모임 목적, 선호 방식과 조율 종료 정책을 입력하여 방을 만들 수 있어야 한다. 종료 정책은 예상 참여 인원, 제출 마감 또는 명시적인 수동 마감 방식 중 하나 이상을 포함해야 하며, 예상 참여 인원을 설정하면 2명 이상 50명 이하여야 한다. 한 방의 실제 참여자도 주최자를 포함해 최대 50명이다. |
| FR-001A | 주최자는 1자 이상 50자 이하의 표시 이름을 입력하고 항상 해당 모임의 참여자가 되어야 한다. 예상 참여 인원에 포함되며 다른 참여자와 동일하게 조건을 제출해야 한다. |
| FR-001B | 주최자는 최대 31일의 후보 탐색 시작일과 종료일을 선택할 수 있어야 한다. 둘 다 생략하면 서버는 방 시간대의 생성일을 시작일로 하고 그 날짜로부터 14일 뒤를 배타적 종료일로 적용해야 하며, 프론트엔드는 선택하지 않을 때 이 기본값이 적용됨을 방 생성 화면에 표시해야 한다. |
| FR-002 | 시스템은 내부 방 UUID와 분리된 추측하기 어려운 128비트 공개 초대 코드로 방 참여 공유 링크를 생성해야 한다. 공개 방 API와 URL은 초대 코드만 사용해야 한다. |
| FR-002A | **Post-MVP:** 주최자는 Google 또는 Kakao 계정으로 로그인해야만 방을 생성하고 주최자 전용 명령을 수행할 수 있어야 한다. 일반 참여자의 서비스 로그인은 선택 사항이어야 한다. |
| FR-002B | **Post-MVP:** 서버는 소셜 로그인 사용자를 식별하고 서비스 계정과 연결해야 한다. |
| FR-002C | 비로그인 참여자는 서버가 발급하여 API 호스트 전용 `Secure HttpOnly; SameSite=Lax; Path=/api` 쿠키로 전달한 30일 고정 수명의 추측하기 어려운 브라우저 단위 불투명 게스트 자격 증명으로 자신의 참여와 제출 소유권을 증명해야 한다. 동일한 유효 자격 증명은 여러 방의 참여를 소유할 수 있지만 방마다 최대 하나의 참여자에만 연결되어야 한다. 자격 증명을 응답 본문, URL 또는 프론트엔드 저장소에 노출해서는 안 되며, 공유 초대 링크만으로는 어떤 참여자의 입력도 조회·수정할 수 없어야 한다. 쿠키 삭제·만료 또는 다른 브라우저·기기에서는 기존 소유권을 자동 복구하지 않는다. |
| FR-002D | **Post-MVP:** 로그인 사용자의 일반 로그아웃은 현재 기기의 Refresh Token 패밀리만 폐기하고 해당 쿠키를 삭제해야 한다. 별도의 모든 기기 로그아웃은 해당 사용자의 모든 Refresh Token 패밀리를 폐기해야 한다. 두 동작 모두 이미 발급된 Access Token을 즉시 폐기하거나 Google·Kakao 계정 및 Calendar 연결을 해제하지 않아야 한다. |
| FR-003 | **Post-MVP:** Google Calendar 연동은 meet-me에 로그인한 참여자에게만 제공해야 한다. 비로그인 게스트의 Calendar OAuth 시작·콜백·토큰 저장을 허용해서는 안 되며, 게스트는 Calendar 대신 해당 방에만 귀속되고 다른 방이나 계정에 재사용되지 않는 일회성 meet-me 시간 격자를 이용할 수 있어야 한다. |
| FR-003A | **Post-MVP:** 로그인한 개인의 Calendar 계정 연결·일정 조회와 현재 참여 중인 방의 매칭 적용을 분리해야 한다. Calendar를 연결한 참여자 본인이 현재 방에서 사용을 ON/OFF할 수 있어야 하며 주최자가 타인의 설정을 대신 변경할 수 없어야 한다. OFF인 Calendar 데이터는 매칭에서 무시해야 한다. 프론트엔드는 해당 참여자·방에서 Calendar를 최초 ON할 때 불가 일정 외 시간이 모두 후보가 될 수 있음을 알리는 확인 팝업을 해당 참여자·방에서 한 번만 표시해야 하며, 백엔드는 별도 확인 필드 없이 `CALENDAR` 입력 모드를 명시적 사용 의사로 취급해야 한다. |
| FR-004 | **Post-MVP:** Google Calendar 데이터는 사용자의 절대 불가 시간 배열로 변환되어야 한다. |
| FR-004A | 제출 MVP의 모든 참여자는 선택적인 부가 기능으로 방 전용 격자에서 가능한 시간을 선택할 수 있어야 한다. 주최자가 날짜 범위를 명시한 방에서는 실제 날짜별 구간을, 날짜 범위를 생략한 방에서는 월요일부터 일요일까지의 주간 반복 구간을 입력하며, 격자 입력은 LLM을 거치거나 다른 방에서 재사용되어서는 안 된다. 빈 수동 가능 시간은 추가 시간 제약이 없다는 뜻이며 `가능 시간 없음`으로 해석해서는 안 된다. Post-MVP Calendar 사용자는 별도의 추가 불가 시간 격자를 사용할 수 있어야 한다. |
| FR-004B | **Post-MVP:** Calendar ON 제출을 접수할 때 서버는 그 시점의 Google Calendar 일정을 조회·정규화하여 해당 불변 제출 버전에 스냅샷으로 저장해야 한다. 입력 수집 종료와 방 전체 배치 고정 시 Google Calendar를 다시 호출해서는 안 되며, 종료 시점의 최신 제출 버전에 저장된 스냅샷만 매칭에 사용해야 한다. |
| FR-005 | 참여자는 시간과 장소 조건을 자연어로 입력할 수 있어야 한다. 자연어를 제공하면 1자 이상 500자 이하이고 공백만으로 구성되지 않아야 하며, 서버는 Unicode 코드 포인트를 기준으로 길이를 검증하고 초과 입력을 자르지 않고 거부해야 한다. 제출 MVP에서는 수동 가능 시간을 하나 이상 선택했다면 자연어 없이도 제출할 수 있어야 한다. |
| FR-006 | 서버는 자연어 속 위치 표현을 특정 가능한 장소, 이동 제약 또는 미확정 장소로 구분하고, 지도 공급자의 전체 노출 가능 정확도순 결과에서 정규화된 장소명이 정확히 일치하는 결과가 하나인 표현만 장소 허용 영역으로 변환해야 한다. |
| FR-006A | `집`, `회사`, `학교 근처`와 같은 개인 기준 표현 및 `중앙역`처럼 하나로 특정되지 않는 표현은 좌표나 장소 후보를 만들지 않아야 하며, 클라이언트에 별도 장소 입력을 요구하지 않아야 한다. |
| FR-007 | 제출 MVP에서는 선택적인 자연어 조건과 방 전용 수동 가능 시간을 한 번에 서버로 보내야 한다. 공백이 아닌 자연어 또는 하나 이상의 수동 가능 시간 중 적어도 하나가 있어야 하며 둘 다 없으면 제출을 거부하고 완료 인원에 포함하지 않아야 한다. Post-MVP에는 Calendar 절대 불가 시간과 선택적인 추가 불가 시간을 가진 `CALENDAR` 모드를 추가하되 상충하는 모드의 필드를 함께 허용해서는 안 된다. |
| FR-007A | 로그인 여부와 관계없이 참여자는 유효한 본인 증명을 거쳐 서버에 저장된 자신의 최신 제출 Payload를 조회할 수 있어야 한다. 다른 참여자의 입력은 조회할 수 없어야 하며, 주최자도 정상 입력이나 기술적 분석 지연 상태의 타인 원문을 조회할 수 없어야 한다. |
| FR-008 | 서버는 입력 수집 종료 시점의 참가자별 최신 제출을 하나의 방 전체 제출 배치로 고정해야 한다. 자연어가 하나 이상이면 자연어가 있는 항목만 묶어 배치당 하나의 논리적 Gemini 파싱 작업을 수행하고, 자연어가 하나도 없으면 Gemini 작업 없이 결정론적 매칭을 시작해야 한다. 참가자별 제출·수정은 별도의 Gemini 작업을 만들지 않으며, 제공된 자연어 합계는 최대 10,000 Unicode 코드 포인트여야 한다. |
| FR-008A | 참여자는 입력 수집이 종료되기 전까지 자신의 조건을 수정할 수 있어야 한다. 수정본은 새 불변 버전으로 저장하되 참여 인원은 중복 집계하지 않으며, 방 전체 제출 배치에는 종료 시점의 최신 버전만 포함해야 한다. |
| FR-008B | 방 전체 Gemini 작업의 기술적 재시도가 소진되면 서버는 입력과 고정 배치를 보존하고 방을 `ANALYSIS_DELAYED`로 전이하되 후보를 생성하지 않아야 한다. Gemini 응답이 성공한 뒤 개별 조건의 의미·스키마·도메인 검증 실패가 발생한 경우에만 유효한 조건과 일정 입력 모드별 정형 시간 구간으로 `PARTIAL` 결과를 생성하고, 해당 미반영 원문과 참여자 식별 정보를 결과 아래에서 주최자에게만 표시해야 한다. |
| FR-008C | 인증된 주최자는 `ANALYSIS_DELAYED` 상태의 고정 배치 분석을 멱등하게 다시 요청할 수 있어야 하며 참여자에게 입력 재제출을 요구해서는 안 된다. 재요청의 자동 수행 여부와 횟수 상한은 별도 의사결정으로 확정한다. |
| FR-009 | 후보 생성 전까지 참여자별 가능 시간과 조건은 다른 참여자에게 공개되지 않아야 한다. 부분 결과에서는 미반영된 원문만 사전 고지에 따라 주최자에게 공개할 수 있으며, 정상 반영된 조건과 다른 참여자에게는 공개하지 않아야 한다. |
| FR-010 | 예상 참여 인원이 설정된 경우 주최자를 포함한 해당 인원수의 고유 참여자 제출이 PostgreSQL에 접수되면 LLM 호출 없이 입력 수집을 종료해야 한다. 제출 마감 도달 또는 주최자의 수동 마감도 입력 수집을 종료하며, 종료 시점의 최신 입력으로 만든 방 전체 제출 배치의 구조화가 종결된 뒤 서버가 결정론적 매칭 알고리즘을 실행해야 한다. |
| FR-010A | 주최자는 예상 참여 인원이나 제출 마감을 설정했더라도 자동 조건 충족 전에 경고와 재확인을 거쳐 수동으로 입력을 마감할 수 있어야 한다. |
| FR-010B | 입력 수집 종료 시 주최자를 포함한 고유 참여자 제출이 2개 미만이면 방을 `INSUFFICIENT_PARTICIPANTS`로 종료하고 후보를 생성하지 않아야 한다. |
| FR-011 | 시스템은 우선순위가 반영된 Plan A, B, C 후보를 종류별 최대 한 장으로 제공해야 한다. 전원 시간 교집합이 없을 때 Plan C는 최소 2명을 유지하며 `N-1`, `N-2` 순으로 탐색하고, 같은 참석 인원 조합은 공통 가능 총시간, 가장 이른 시작, 안정적인 내부 식별자 순으로 결정해야 한다. 후보가 없으면 정상 완료 상태 `NO_MATCH`를 제공해야 한다. |
| FR-011A | 서버는 탐색 범위에서 자연어 시간 조건을 실제 날짜별 구간으로 확장한 뒤 해당 후보에 포함되는 모든 참여자의 Calendar 불가 시간을 차감하고 남은 모든 연속 가능 구간을 후보로 만들어야 한다. 후보 응답은 언어 중립적인 구조화 결과와 서버 i18n 템플릿으로 생성한 자연어 요약을 함께 제공해야 하며, 요약은 구조화 결과에 없는 가능 시간이나 제외된 날짜를 포함해서는 안 된다. |
| FR-012 | 주최자만 후보 중 하나를 최종 결과로 확정할 수 있어야 한다. |
| FR-012A | `PARTIAL` 결과에서도 주최자에게 다른 참여자의 원문 수정·재처리 책임이나 별도 확인 단계를 요구하지 않아야 한다. 화면은 확정 버튼 문구로 부분 결과임을 드러내고 기존의 원클릭 확정 흐름을 유지해야 한다. |
| FR-012B | 같은 후보의 반복 확정은 멱등하게 기존 결과를 반환하고, 서로 다른 후보의 동시·중복 확정은 먼저 커밋된 선택만 유지한 채 충돌로 거부해야 한다. |
| FR-013 | MVP의 방 시간대는 `Asia/Seoul`로 고정하되 IANA Time Zone ID로 저장해야 한다. 절대 시점은 UTC로 저장하고 자연어·반복 조건은 방 시간대의 지역 날짜·시간으로 해석한 뒤 DST 규칙을 적용할 수 있어야 한다. |
| FR-014 | MVP의 지원 locale은 `ko-KR`로 고정하되 사용자 노출 문구는 i18n 리소스로 관리해야 한다. API는 언어 중립적인 상태·오류 코드를 제공하고 요청 locale을 BCP 47 형식으로 다룰 수 있어야 한다. |

## 7. 핵심 비즈니스 규칙

### Rule 1. 참가자 입력과 방 전체 배치 AI 호출

사용자가 제출 버튼을 누르면 클라이언트는 다음 데이터를 하나의 Payload로 서버에 전송한다.

| 필드 | 의미 | 필수 여부 |
| --- | --- | --- |
| `raw_text` | 사용자가 입력한 자연어 조건. 예: "목요일 학교 앞 가능" | 수동 가능 시간이 하나 이상이거나 `CALENDAR` 모드이면 생략 가능. 제공하면 공백이 아닌 1~500 Unicode 코드 포인트 |
| `schedule_input_mode` | 방에서 실제로 적용할 일정 입력 기준. `MANUAL_AVAILABILITY` 또는 Calendar 사용 ON을 뜻하는 `CALENDAR` | 필수 |
| `manual_available_times` | 방 전용 격자에서 선택한 실제 날짜별 또는 주간 반복 가능 시간 구간 | `MANUAL_AVAILABILITY` 모드의 선택적 부가 입력. 빈 배열은 추가 시간 제약 없음 |
| `calendar_blocked_times` | Google Calendar 연동으로 수집한 절대 불가 시간 배열. 일정이 없으면 빈 배열도 유효한 스냅샷 | `CALENDAR` 모드에서 사용 |
| `additional_blocked_times` | Calendar에 잡히지 않은 절대 불가 시간을 보완한 실제 날짜별 또는 주간 반복 구간 | `CALENDAR` 모드에서 선택, 사용하지 않으면 빈 배열 |

서버는 Payload를 받은 뒤 다음 규칙을 지킨다.

1. `raw_text`가 제공되면 공백이 아닌 1자 이상 500자 이하로 제한하고 Unicode 코드 포인트를 기준으로 검증한다. 초과 입력은 조용히 자르지 않고 현재 길이와 최대 길이를 포함한 언어 중립 오류 코드로 거부한다. 공백이 아닌 자연어, 현재 방의 Calendar ON, 하나 이상의 `manual_available_times` 중 어느 것도 없으면 언어 중립 오류 코드 `SUBMISSION_INPUT_REQUIRED`로 제출을 거부하고 완료 인원을 증가시키지 않는다. `CALENDAR`는 방별 ON 선택과 유효한 Calendar 스냅샷이 있으면 자연어 없이 접수한다.
2. 최초 제출과 각 수정본을 불변 제출 버전으로 구분하되, 참가자의 제출·수정 시점에는 Gemini 작업을 만들지 않는다.
3. 수정본이 접수되면 최신 버전 참조를 교체한다. Calendar ON 제출 또는 수정은 접수 시점의 Calendar 스냅샷을 각 제출 버전에 함께 고정하며, 입력 수집 종료 시점의 최신 버전과 그 스냅샷만 방 전체 제출 배치에 포함한다.
4. 배치에 포함된 비어 있지 않은 모든 `raw_text`의 합계는 최대 10,000 Unicode 코드 포인트로 제한한다. 최초 제출 또는 수정으로 합계가 상한을 넘으면 해당 요청을 거부하며 원문을 자르지 않는다.
5. 입력 수집 종료 트랜잭션은 최신 제출 버전의 식별자를 하나의 불변 방 전체 제출 배치로 고정한다. 비어 있지 않은 `raw_text`가 하나 이상일 때만 배치당 하나의 논리적 Gemini 파싱 작업과 Outbox 이벤트를 만들고, 하나도 없으면 AI 작업 없이 결정론적 매칭 작업을 시작한다.
6. 비동기 Worker는 PostgreSQL에서 배치를 조회하고 참가자 실명 대신 불투명 입력 참조값과 비어 있지 않은 최신 `raw_text`, 방 Time Zone ID와 입력 locale 문맥을 하나의 Gemini Structured Output 요청으로 전달한다. 자연어가 없는 참여자는 요청 항목에서 제외하며 Calendar 불가 시간, 방 전용 가능 시간과 추가 불가 시간도 전달하지 않는다.
7. 논리적 작업은 최초 호출 1회와 최대 3회의 기술적 재시도로 구성한다. 네트워크 오류, timeout, HTTP 429 또는 공급자 5xx에만 재시도하며, 의미 파싱·스키마·도메인 검증 실패에는 재호출하지 않는다.
8. 재시도는 Full Jitter 지수 백오프를 사용한다. `Retry-After`가 없으면 1·2·3차 재시도 전에 각각 `0~1초`, `0~2초`, `0~4초` 범위에서 무작위 지연하고, 유효한 `Retry-After`는 남은 전체 처리시간 안에서 우선 적용한다. 호출별 timeout은 15초, 논리적 작업의 전체 timeout은 60초다.
9. 서버는 배치 응답의 불투명 참조값과 입력 수가 요청과 일치하는지 확인하고 각 참가자 결과를 독립적으로 재검증한다. 실제 호출 횟수, 응답이 제공한 토큰 사용량과 추정 비용은 재시도를 포함해 기록한다.
10. 정형화된 자연어 조건, 일정 입력 모드, Calendar 불가 시간, 방 전용 가능 시간과 추가 불가 시간을 데이터베이스에 저장한다. 배치 전체의 기술적 재시도가 소진되면 입력과 배치 스냅샷, 실패 분류와 시도 메타데이터를 보존하고 방을 `ANALYSIS_DELAYED`로 전이하며 후보를 계산하지 않는다. 원본 Stream 메시지는 ACK하고, 주최자의 재요청은 같은 고정 배치를 대상으로 새 Outbox 이벤트를 멱등하게 발행한다.
11. 장소 표현은 지도 공급자의 검색 결과를 서버가 재검증하며, LLM이 좌표를 만들거나 모호한 검색 결과 중 하나를 임의로 선택하지 않는다.
12. 시간 구간과 정형 위치 조건의 상세 JSON 스키마, 검증 규칙, 오류 응답은 아키텍처 설계에서 확정한다.

### Rule 2. 장소 허용 영역과 이동 제약

지도 공급자는 자연어에서 추출한 장소 표현의 검색·정규화에 사용하고, 거리와 영역 교집합은 검증된 위도·경도를 기준으로 서버가 계산한다.

- **장소 특정 가능성:** 지도 공급자가 하나의 위치로 검증한 표현만 좌표를 가진 장소가 된다. 모호한 검색 결과의 첫 항목을 자동 선택하지 않는다.
- **Kakao 고유성:** 질의를 Unicode NFKC로 정규화하고 앞뒤·연속 공백과 대소문자를 정리한 뒤, Kakao Local의 전체 노출 가능 정확도순 결과에서 장소명이 정확히 일치하는 결과가 하나일 때만 정규화한다. 0개 또는 복수이면 미반영 장소로 남기고 첫 결과를 임의 채택하지 않는다.
- **이동 제약:** `집`, `회사`, `학교 근처`처럼 개인 기준점 없이는 특정할 수 없는 표현은 장소가 아니라 강한 이동 제약으로 보존한다. 이 조건 분기는 오프라인 장소 후보를 만들 수 없으며 온라인 후보로 fallback할 수 있다.
- **미확정 장소:** `중앙역`처럼 하나로 특정할 수 없는 표현은 미확정 상태로 보존하고 장소 후보나 좌표를 만들지 않는다.
- **허용 반경:** 사용자가 거리를 명시하면 그 값을 사용하고, 특정 가능한 장소에 별도 거리가 없으면 기본 1km 허용 반경을 적용한다.
- **개인 허용 영역:** 한 참여자가 대안으로 제시한 특정 가능한 장소가 여러 개면 각 장소 원의 합집합을 그 참여자의 허용 영역으로 본다.
- **그룹 교집합:** 오프라인 후보는 관련 참여자 모두의 허용 영역 교집합 안에 있어야 한다. 예를 들어 `봉천역`과 `서울대입구역`의 허용 원이 겹치면 두 역 사이의 공통 영역에서 후보를 만들 수 있다.
- **대표 지점:** 오프라인 후보는 허용 영역 교집합 내부에서 경계까지의 최소 여유 거리가 가장 큰 결정론적 대표 지점을 사용한다. 실제 매장을 자동 선택하지 않고 개별 참여자의 장소명을 노출하지 않는 `공통 가능 지역`으로 표시한다.
- 장소 판정, 거리와 영역 교집합은 LLM 응답이 아니라 서버의 결정론적 계산 결과만 사용한다.

### Rule 3. Plan A, B, C와 Fallback

입력 수집이 종료되고 접수된 조건이 준비되면 서버는 다음 순서로 후보를 계산한다.

1. **Plan A — 최적안:** 전원이 참석 가능한 시간이며 오프라인 장소 조건을 충족한다.
2. **Plan B — 대안안:** 전원이 참석 가능한 시간이며 온라인 조건을 충족한다. 오프라인 교집합이 없거나 한 명 이상이 오프라인 불가 조건을 설정한 경우 우선적인 대안이 된다.
3. **Plan C — 차선·다수결안:** 전원이 겹치는 시간이 전혀 없을 때 참석 가능한 인원이 가장 많은 시간부터 탐색한다. `N-1명`, `N-2명` 순으로 후보를 찾고 해당 참석자들의 장소 선호를 반영한다.

Plan C는 최소 2명 미만으로 낮추지 않는다. 같은 참석 인원 후보가 여러 개면 공통 가능 총시간이 긴 참여자 조합, 가장 이른 시작, 정렬된 내부 참여자 식별자 순으로 하나를 선택한다. 후보가 하나도 없으면 조율 작업은 실패가 아니라 `NO_MATCH`로 정상 완료한다.

후보 선택과 순위 계산은 AI가 아닌 서버 알고리즘으로 수행한다. 후보가 세 개 미만이면 존재하는 플랜 카드만 반환하고, 동률은 위의 결정론적 순서로 해소한다.

시간 후보는 방의 탐색 날짜 범위 안에서 다음 순서로 만든다.

1. 자연어에서 구조화한 요일·시간 조건을 방 시간대의 실제 날짜별 구간으로 확장한다. 자연어 시간 조건이 없으면 탐색 범위 전체를 중립적인 기준 구간으로 사용한다.
2. `MANUAL_AVAILABILITY` 참여자가 방 전용 가능 시간을 하나 이상 선택했다면 기준 구간과 그 가능 시간의 교집합만 유지한다. 빈 배열이면 부가 슬롯 제약을 적용하지 않고 기준 구간을 그대로 유지한다. 주간 반복 가능 시간은 서버의 실제 후보 탐색 범위에 날짜별로 펼쳐 적용한다.
3. `CALENDAR` 참여자는 자연어가 없으면 방의 전체 탐색 범위를 기준 구간으로 삼고 Calendar 절대 불가 시간과 추가 불가 시간의 합집합을 차감한다. 즉 ON 확인은 Calendar에 잡힌 불가 일정 외 시간이 후보가 되어도 된다는 뜻이며, 남은 범위는 다른 참여자의 조건과 교차해 좁힌다. 자연어가 있으면 그 가능 구간을 기준으로 사용하고, 주간 반복 추가 불가 시간은 실제 후보 탐색 범위에 날짜별로 펼쳐 적용한다.
4. 교집합 또는 차감 후 남은 모든 연속 구간을 구조화된 후보에 포함한다.
5. 서버는 구조화된 후보를 기준으로 i18n 자연어 요약을 생성한다. 정형 일정 입력 때문에 제외된 날짜나 잘린 시간대를 가능한 것으로 표현해서는 안 된다.
6. 여러 실제 날짜를 `평일 18:00~21:00`처럼 묶어 표현할 수 있지만 이는 반복 일정이 아니라 탐색 범위의 결과 요약이며, 실제 날짜는 주최자가 정해 공지한다.
7. 반복 요일·시간 조건은 실제 가능 날짜 나열과 `패턴 + 모든 예외`를 손실 없이 만들 수 있을 때만 압축한다. 완전히 제외되거나 일부 시간만 남은 날짜를 각각 예외 한 건으로 세며, 예외 건수가 실제 가능 날짜 건수보다 적을 때 패턴 표현을 선택한다. 두 건수가 같거나 예외가 더 많으면 실제 가능 날짜와 시간을 나열한다.
8. 특정 날짜 조건이거나 손실 없는 반복 패턴을 만들 수 없는 불규칙한 후보는 실제 날짜와 시간을 나열한다. `대체로`, `보통`처럼 일부 예외를 숨기는 근사 표현은 사용하지 않는다.

### Rule 4. 입력 수집 종료 정책

- 주최자는 항상 첫 번째 참여자이며 예상 참여 인원은 주최자를 포함한 전체 참여자 수를 의미한다.
- 주최자도 다른 참여자와 동일하게 조건을 제출해야 완료 인원으로 계산할 수 있다.
- 예상 참여 인원 `N`은 50명 하드 상한 안에서 입력 수집을 자동 종료하기 위한 고유 참여자 제출 목표이며 가입 정원과는 별개다.
- 예상 참여 인원을 설정하는 경우 최소값은 2명이다.
- 제출 완료 인원은 원본 입력이 PostgreSQL에 정상 저장된 고유 참여자 수로 계산하며 LLM 구조화 완료 여부와 분리한다.
- 한 참여자의 수정본은 완료 인원을 증가시키지 않는다.
- 데드라인 기반 방은 데드라인 도달 전까지, 참여 인원 기반 방은 `N`번째 고유 참여자의 최초 제출이 접수되기 전까지, 수동 마감 방은 주최자가 마감하기 전까지 수정할 수 있다. 종료 조건을 함께 설정한 경우 가장 먼저 충족된 시점까지만 수정할 수 있다.
- 예상 참여 인원수의 제출이 접수되면 입력 수집을 즉시 종료하고, 종료 시점의 최신 입력을 묶은 방 전체 제출 배치의 구조화가 종결된 뒤에만 매칭을 시작한다.
- `N`번째 제출과 이후 제출이 경합하면 서버가 원자적으로 `N`번째 제출까지만 접수하고 방을 마감하며, 마감 후 도착한 제출은 반영하지 않는다.
- 수정 요청과 종료 조건이 경합하면 서버에 먼저 커밋된 상태를 기준으로 처리하며, 입력 수집 종료 이후에는 결과 생성 전이라도 수정할 수 없다.
- 주최자는 방을 만들 때 예상 참여 인원과 제출 마감을 각각 선택적으로 설정할 수 있다.
- 예상 참여 인원과 제출 마감을 모두 설정하지 않으면 수동 마감 방식을 명시적으로 선택해야 한다.
- 예상 참여 인원 또는 제출 마감이 설정되어도 주최자의 수동 마감은 항상 허용한다.
- 둘 이상의 자동 종료 조건을 설정하면 가장 먼저 충족된 조건이 입력 수집을 종료한다.
- 자동 종료 조건을 충족하기 전에 수동 마감하면 아직 제출하지 않은 참여자가 있을 수 있음을 경고하고 주최자의 재확인을 받는다.
- 데드라인 도달 또는 수동 마감 시 접수된 고유 참여자 제출이 주최자를 포함해 2개 미만이면 `INSUFFICIENT_PARTICIPANTS`로 종료하고 Plan 후보를 만들지 않는다.
- 입력 수집 종료와 후보 생성 완료는 서로 다른 상태다. 종료 후 방 전체 제출 배치는 비동기로 구조화되며 참가자 요청은 Gemini 응답과 매칭 완료를 기다리지 않는다.

### Rule 5. 파싱 실패와 부분 결과

- 자연어가 포함되어 Gemini 호출이 필요한 방에서 기술적 재시도가 소진되면 의미 파싱 결과가 없는 상태이므로 `PARTIAL` 후보를 만들지 않는다. 방은 `ANALYSIS_DELAYED`가 되고 참여자 입력과 고정 배치는 PostgreSQL에 유지된다. 자연어가 전혀 없는 방은 Gemini를 호출하지 않으므로 이 실패 상태를 거치지 않는다.
- `ANALYSIS_DELAYED`에서는 프론트엔드가 무기한 로딩하지 않고 저장 완료와 분석 지연 상태를 표시한다. 주최자는 방 단위 재분석을 요청할 수 있고 참여자는 입력을 다시 제출하지 않는다.
- 기술적 전체 장애를 이유로 타인의 모든 원문을 주최자에게 공개하지 않는다. 각 참여자는 본인 증명을 거쳐 자신의 최신 제출만 다시 조회할 수 있다.
- 서버는 LLM 결과를 조건 단위로 검증하고 해석 가능한 조건은 유지하며, 의미가 없거나 스키마·도메인 검증을 통과하지 못한 조건만 매칭 입력에서 제외한다.
- 자연어 전체를 해석할 수 없으면 해당 참여자의 자연어 제약만 제외한다. Calendar 절대 불가 시간, 방 전용 가능 시간과 추가 불가 시간처럼 독립적으로 유효한 정형 입력은 계속 반영한다.
- 개별 조건의 의미·스키마·도메인 검증 실패는 같은 배치를 자동으로 다시 호출하지 않는다.
- 하나 이상의 최신 제출 버전에 미반영 원문이 있으면 후보 집합을 `PARTIAL`로 표시한다. 후보가 어떤 Plan 유형이더라도 모든 자연어 조건을 충족했다고 표현하지 않는다.
- 부분 결과에는 반영된 제출 수, 전체 제출 수와 미반영 입력 수를 표시한다.
- 결과 아래의 주최자 전용 `미반영 입력`에는 참여자 표시 이름, 실패한 원문과 미반영 사유를 안전한 일반 텍스트로 제공한다. 이는 결과가 부분적인 이유를 설명하는 참고 정보이며 주최자가 수정하거나 재처리해야 할 작업이 아니다.
- 정상적으로 반영된 다른 참여자의 조건은 계속 비공개로 유지하고, 미반영 원문은 주최자 이외의 참여자에게 공개하지 않는다.
- 별도 알림이나 실패 참여자만을 위한 입력 재개는 MVP에서 제공하지 않는다.
- 제출 화면은 AI가 해석하지 못한 조건이 일정 결정을 위해 주최자에게 공개될 수 있음을 제출 전에 고지한다.
- 주최자는 다른 참여자의 제출을 수정하거나 파싱을 다시 요청할 수 없다.
- 별도의 확인 체크박스나 경고 모달을 추가하지 않는다. `PARTIAL` 배지와 `부분 결과로 확정`처럼 상태가 드러나는 확정 버튼 문구로 안내하고, 버튼 클릭 자체로 최종 확정한다.

### Rule 6. 시간대와 locale

- 모든 방은 IANA Time Zone ID를 가진다. MVP에서는 주최자가 선택하지 않으며 서버가 `Asia/Seoul`만 허용한다.
- 데드라인과 생성·수정·확정 시각처럼 절대적인 시점은 UTC로 저장한다.
- 자연어 시간과 반복 가능 조건은 방의 지역 날짜·시간 및 Zone ID를 유지하고, 후보 탐색 시 해당 날짜의 IANA timezone database 규칙으로 UTC 시점에 변환한다.
- API의 절대 시각은 ISO 8601 offset을 포함하고, 방 응답에는 Time Zone ID를 함께 제공한다.
- locale은 BCP 47 언어 태그를 사용한다. MVP에서는 `ko-KR`만 지원하고 지원하지 않는 값은 `ko-KR`로 fallback한다.
- API 상태·오류 코드는 locale과 무관하게 고정한다. 서버가 만드는 사용자 노출 메시지는 i18n message bundle에서 조회하며 프론트엔드는 코드 기반 자체 번역도 할 수 있다.
- 자연어 제출 버전에는 입력 locale을 기록하고, LLM Structured Output은 언어에 의존하지 않는 서버 스키마로 변환한다.
- 후보 탐색 기간은 방 시간대의 지역 날짜로 표현하고 `[searchStartDate, searchEndDate)`의 반개구간을 사용한다.
- `searchEndDate`는 `searchStartDate`보다 뒤여야 하며 날짜 차이는 최대 31일이다.
- 주최자가 시작일과 종료일을 모두 생략하면 서버는 방 생성 시점의 지역 날짜를 `searchStartDate`, 그 날짜에 14일을 더한 값을 `searchEndDate`로 확정하여 저장한다. 즉 생성일을 포함한 14개의 지역 날짜가 대상이다.
- 서버는 주최자가 범위를 명시했는지 또는 기본 14일을 적용했는지도 함께 보존한다. 날짜를 명시한 방은 수동 가능·추가 불가 시간을 실제 날짜형으로, 생략한 방은 주간 반복형으로만 접수하며 주간 반복형은 기본 14일 범위에 펼쳐 계산한다.
- 시작일과 종료일 중 하나만 전달하면 요청을 거부한다. 프론트엔드는 두 값을 선택하지 않을 때 `오늘부터 14일간 탐색`과 같이 서버 기본값을 명시적으로 안내한다.
- 서버는 기본값 적용 여부와 관계없이 방 조회 응답에 확정된 `searchStartDate`, `searchEndDate`를 반환하며 후보는 이 범위 밖에 생성하지 않는다.

## 8. 시스템 제약사항

### 기본 기술 스택

- 서버 프레임워크: Spring Boot
- 서버 언어: Kotlin
- 주 데이터베이스: PostgreSQL
- 데이터베이스 마이그레이션: Flyway
- 인메모리 데이터 저장소: Redis
- 리버스 프록시: Nginx
- Infrastructure as Code: Terraform
- 국제화: Spring MessageSource 기반 i18n, MVP locale `ko-KR`
- 저장소 범위: 백엔드 애플리케이션, 데이터베이스 연동, 외부 API 연동 및 서버 측 비즈니스 로직

### 개발 및 배포 환경

- 개발은 로컬 환경에서 수행한다.
- 운영 PostgreSQL은 Amazon RDS로 분리한다.
- 운영 컴퓨팅 환경은 Amazon EC2와 Amazon ECS 중에서 추후 결정한다.
- 컨테이너 이미지 레지스트리는 Docker Hub와 Amazon ECR 중에서 추후 결정한다.
- RDS와 운영 컴퓨팅 환경을 포함한 AWS 인프라는 Terraform 코드로 관리한다.
- Nginx와 Redis의 운영 배치 방식은 최종 컴퓨팅 환경에 맞춰 결정한다.
- 로컬 PostgreSQL과 Redis는 Docker Compose로 실행하고 데이터베이스 통합 테스트는 실제 PostgreSQL Testcontainers를 사용한다. 애플리케이션 패키징 방식, 배포 자동화와 환경별 설정 전략은 아키텍처 설계에서 확정한다.

### 인증

- 로그인 공급자: Google, Kakao
- 이메일·비밀번호 기반 자체 인증은 MVP에서 구현하지 않는다.
- meet-me 서비스 인증은 15분 수명의 RS256 JWT Access Token과 Redis TTL로 관리하는 회전형 불투명 Refresh Token을 사용한다. JWT는 `kid`로 검증 키를 선택하며 현재 서명용 private key와 교체 중인 이전 public key를 분리해 관리한다. Refresh Token은 미사용 14일 후 만료되고 토큰 패밀리는 최초 로그인부터 최대 30일 유지된다. Access Token은 로그인·갱신 응답 body로 전달하고 이후 `Authorization: Bearer` 헤더로 사용한다. Refresh Token은 프론트엔드와 API가 같은 상위 사이트의 서브도메인에 배포된다는 전제에서 API 호스트 전용 `Secure HttpOnly; SameSite=Lax; Path=/api/auth` 쿠키의 `Set-Cookie` 헤더로만 전달하고, `Max-Age`는 미사용 14일과 토큰 패밀리 잔여 절대 수명 중 짧은 값으로 맞춘다. Refresh·로그아웃 요청은 정확한 프론트엔드 Origin 허용 목록으로 검증한다. 공급자 OAuth/OIDC 처리 방식과 계정 연결 정책은 아키텍처 설계에서 확정한다.
- 일반 로그아웃은 현재 기기의 Refresh Token 패밀리와 쿠키만 폐기하고, 별도의 모든 기기 로그아웃은 사용자의 모든 Refresh Token 패밀리를 폐기한다. 두 경우 모두 이미 발급된 Access Token은 최대 15분 동안 유효할 수 있으며 Google·Kakao 로그인 연결과 Google Calendar grant는 별도의 연결 해제 전까지 유지한다.

### API 문서

- 프론트엔드는 백엔드가 생성한 Swagger/OpenAPI 문서를 API 계약으로 사용한다.
- 모든 Controller 엔드포인트의 주요 응답은 `@ApiResponse`로 문서화한다.
- 요청 및 응답 DTO에는 `@Schema`를 추가하여 필드 의미와 제약을 문서화한다.

### 자연어 조건 파싱

- 모델: Google Gemini Flash 계열, 정확한 모델 ID는 아키텍처 결정에서 확정
- 연동: 공식 Google GenAI SDK의 Java 클라이언트를 AI Adapter 내부에서 사용
- 기능: JSON Schema 기반 Structured Output을 통한 JSON 형식 강제
- 호출 제한: 입력 수집 종료 시 만든 방 전체 제출 배치에 자연어가 하나 이상 있을 때만 논리 파싱 작업 하나. 자연어 없는 참여자는 요청에서 제외하며 전원이 정형 일정 입력만 제출했으면 호출하지 않는다. 최초 1회와 Full Jitter 지수 백오프를 적용한 기술적 재시도 최대 3회
- 입력 제한: 참가자별 자연어 최대 500 Unicode 코드 포인트, 방 전체 배치 합계 최대 10,000 Unicode 코드 포인트

### 결정론적 매칭

- 서버에서 참여자별 가능 시간과 장소 조건을 계산한다.
- 시간 계산에는 Set 연산 또는 동일한 결정론적 방식을 사용한다.
- 동일한 입력에는 항상 동일한 결과가 나와야 한다.
- LLM 출력은 계산 입력으로만 사용하며 최종 교집합 계산을 위임하지 않는다.

### 애플리케이션 아키텍처

- 백엔드는 헥사고날 아키텍처를 적용한다.
- 일정 매칭을 포함한 핵심 도메인 로직은 Spring, 데이터베이스, 캐시, AI·OAuth·지도 API와 같은 외부 기술에 직접 의존하지 않는다.
- 애플리케이션은 유스케이스와 포트를 통해 도메인을 호출하고, 웹·영속성·외부 API 연동은 어댑터로 분리한다.
- 구체적인 모듈 및 패키지 구조와 트랜잭션 경계는 `docs/ARCHITECTURE.md`에서 확정한다.

> 2026-09-04 기준 Google 공식 문서에서 Gemini Flash 계열의 멀티모달 입력과 JSON Schema 기반 Structured Output 지원을 확인했다. 실제 구현 전 정확한 stable 모델 ID와 최신 가격을 확정한다.

## 10. MVP 완료 조건

- 주최자가 방을 생성하고 참여 링크를 공유할 수 있다.
- 주최자가 첫 번째 참여자로 등록되고 예상 참여 인원에 포함되며 자신의 조건을 제출할 수 있다.
- 주최자가 예상 참여 인원, 제출 마감 또는 수동 마감 방식을 하나 이상 선택할 수 있다.
- 예상 참여 인원은 2명 이상이며, 어떤 종료 방식이든 제출 참여자가 2명 미만이면 후보가 생성되지 않는다.
- 자동 종료 조건이 있더라도 주최자가 경고와 재확인 후 입력을 조기 마감할 수 있다.
- 제출 MVP에서는 로그인 없이 방을 만들 수 있으며, 방을 만든 익명 브라우저 세션만 주최자 전용 명령을 수행할 수 있다. Google·Kakao 로그인 기반 주최자 전환은 Post-MVP에서 제공한다.
- 일반 로그아웃은 현재 기기만 종료하고 별도의 모든 기기 로그아웃으로 사용자의 모든 Refresh 세션을 종료할 수 있으며, 서비스 로그아웃만으로 공급자 계정·Calendar 연결이 해제되지 않는다.
- 참여자는 로그인 여부와 관계없이 유효한 본인 증명으로 자신의 최신 제출을 다시 조회할 수 있다. 게스트 자격 증명은 브라우저 단위 `Secure HttpOnly` 쿠키로만 전달하며 공유 링크만으로는 제출 소유권을 얻지 못한다. 같은 게스트 브라우저 세션이 같은 방에 다시 접근하면 기존 참여자를 식별해야 한다.
- 로그인한 참여자는 Google Calendar에서 절대 불가 시간을 가져오거나 연동을 건너뛸 수 있고, 비로그인 게스트에게는 Calendar OAuth를 제공하지 않는다.
- Calendar ON 제출 시점의 일정을 제출 버전에 고정하고, 입력 수집 종료 시에는 Google Calendar를 다시 호출하지 않은 채 최신 제출 버전의 스냅샷으로 동일한 결과를 재현할 수 있다.
- Calendar 연결·일정 조회와 방별 적용이 분리되어, 방에서 OFF이면 불러온 일정도 무시하고 ON이면 자연어 없이 Calendar 불가 일정 외 범위를 후보로 허용할 수 있다. 프론트엔드는 참여자·방별 최초 ON 때 이 의미를 확인하는 팝업을 한 번만 표시한다.
- 비로그인 게스트가 해당 방에만 귀속되고 다른 방·계정에 재사용되지 않는 일회성 meet-me 시간 격자를 사용할 수 있다.
- 비로그인 또는 Calendar OFF 참여자가 방 전용 가능 시간 격자를 사용하고, Calendar ON 참여자는 필요할 때만 추가 불가 시간 격자를 사용할 수 있다. 명시한 날짜 범위에서는 실제 날짜형으로, 범위를 생략하면 7일 주간 반복형으로 제출할 수 있다.
- 참여자가 기본 일정 연동 여부를 선택하고 자연어 조건을 제출할 수 있다.
- 참여자가 입력 수집 종료 전까지 자신의 조건을 수정하고 현재 수정 가능 여부를 확인할 수 있다.
- 별도 장소 입력이나 지도 UI 없이 자연어 속 특정 가능한 장소, 이동 제약과 미확정 장소를 구분할 수 있다.
- 특정 가능한 장소만 좌표와 허용 영역을 만들고, 개인 기준 표현과 미확정 장소는 장소 후보를 만들지 않는다.
- 조율 완료 전에는 다른 참여자의 개별 일정과 조건이 노출되지 않는다.
- 입력 수집 종료 전 제출·수정에는 Gemini 작업을 만들지 않고, 종료 시점의 최신 입력을 묶은 방 전체 제출 배치에 자연어가 있을 때만 논리 파싱 작업 하나를 생성하며 기술적 오류 외에는 자동 재호출하지 않는다. 전원이 정형 일정만 제출한 경우 AI 호출 없이 매칭할 수 있다.
- 자연어 또는 수동 가능 시간 중 하나만으로도 제출할 수 있고, 빈 수동 가능 시간은 `가능 시간 없음`이 아니라 부가 슬롯 제약 없음으로 처리할 수 있다.
- 공백이 아닌 자연어, 현재 방의 Calendar ON, 하나 이상의 수동 가능 시간이 모두 없으면 `SUBMISSION_INPUT_REQUIRED`로 거부하고 제출 완료 인원에 포함하지 않는다.
- 제공된 참가자별 자연어 500자와 방 전체 합계 10,000자 제한을 초과한 입력을 자르지 않고 거부할 수 있다.
- 해석 불가능한 조건이 있어도 유효한 입력으로 부분 결과를 만들고, 미반영 원문은 사전 고지 후 주최자에게만 표시할 수 있다.
- Gemini 기술적 재시도 소진 시 후보를 만들지 않고 `ANALYSIS_DELAYED`로 전이하며, 저장된 입력을 재제출하지 않고 주최자가 방 단위 분석을 다시 요청할 수 있다.
- 부분 결과에서도 주최자의 수정·재입력 요청이나 별도 확인 단계를 만들지 않고 상태가 드러나는 버튼으로 원클릭 확정할 수 있다.
- MVP 화면은 `Asia/Seoul`과 `ko-KR`로 동작하지만 방의 Time Zone ID, UTC 시점, 언어 중립 코드와 i18n 리소스 경계를 검증할 수 있다.
- 주최자가 후보 탐색 날짜 범위를 선택할 수 있고, 생략 시 프론트엔드가 오늘부터 14일이라는 기본값을 표시하며 서버도 동일한 범위를 확정하여 적용한다.
- 수정해도 참여 완료 인원은 중복 집계되지 않고 종료 시점의 최신 제출 버전만 매칭에 사용된다.
- 명시된 반경 또는 기본 1km 반경을 적용한 참여자별 허용 영역의 교집합이 서버 계산에 적용된다.
- 전원 참석 가능한 후보가 있으면 Plan A 또는 Plan B가 생성된다.
- 전원 참석 가능한 후보가 없으면 최대 참석 인원 기준의 Plan C가 생성된다.
- Calendar 불가 시간을 제외한 모든 연속 가능 구간과 이에 의미가 일치하는 자연어 요약을 함께 조회할 수 있다.
- 주최자가 후보 플랜을 최종 결과로 확정하고 공유한 뒤 실제 모임 날짜를 직접 공지할 수 있다.
- 모임 1건당 AI API 비용을 측정할 수 있고 MVP 상한인 10원 미만인지 확인할 수 있다.
- 공개 익명 API의 과도한 방 생성·참여·제출·주최자 명령을 제한하고, Redis 장애가 저장된 입력과 고정 배치의 영구 유실로 이어지지 않아야 한다.
- 종료 또는 생성 후 30일이 지난 제출 MVP 방의 원문·일정·정규화 좌표·후보와 참조되지 않는 만료 게스트 세션을 삭제할 수 있어야 한다.

## 11. 후속 결정 필요 사항

다음 항목은 제품 요구사항의 의도는 유지하되, 기술 스택 논의와 함께 `docs/ARCHITECTURE.md` 및 `docs/ADR.md`에서 구체화한다.

- MVP 이후 방별 시간대 선택 UI와 허용할 IANA Time Zone 목록
- 다국어 지원 순서, 사용자 선호 locale의 저장 위치와 locale 결정 우선순위
- 가능 시간·추가 불가 시간 격자의 5분·10분 입력 간격, 하루 표시 시간 범위와 긴 날짜 범위의 페이지 이동 방식
- 후보 점수 계산식과 동률 해소 규칙
- 세 개 미만의 유효 후보가 존재할 때의 UI 표현
- Gemini 배치의 자연어가 짧더라도 입력별 구조화 조건을 최대 32개, 응답 본문을 최대 256KiB로 제한한다.
- **Post-MVP:** Gemini 배치 실패·지연과 Worker poison message를 Grafana Cloud로 알릴 임계값·연락 채널
- 장소 검색·정규화와 결과 표시용 이름 조회에 사용할 지도 공급자
- 허용 영역 교집합에서 대표 지점과 실제 모임 장소 후보를 만드는 방식
- Google Calendar 인증 범위와 데이터 동기화 방식
- Google Calendar 동기화 실패 시 재시도와 수동 대체 UX
- 에브리타임 시간표 입력을 MVP 이후 어떤 방식으로 지원할지
- Google·Kakao OAuth/OIDC 리다이렉트, meet-me RS256 운영 키 생성·비밀 저장소·교체 절차, 공급자 토큰 암호화, 계정 연결 정책과 주최자 권한 검증
- 같은 기기에서 여러 사람이 같은 방에 참여해야 할 때의 계정·세션 전환 UX
- `ANALYSIS_DELAYED` 상태 갱신을 Polling, SSE 또는 WebSocket 중 어떤 방식으로 전달할지
- Post-MVP Refresh Token Redis key·TTL과 운영 Redis 배치·백업 정책
- Nginx의 TLS 종료, 라우팅, 정적 응답 및 요청 제한 범위
- 운영 컴퓨팅 환경으로 EC2와 ECS 중 무엇을 사용할지
- 컨테이너 이미지 레지스트리로 Docker Hub와 ECR 중 무엇을 사용할지
- Nginx와 Redis의 운영 배치 및 애플리케이션 배포 자동화 수준
- Terraform 상태 저장소, 환경 분리 및 비밀정보 주입 방식
- 헥사고날 아키텍처의 모듈·패키지 구조와 트랜잭션 경계
- Post-MVP Calendar 일정·공급자 토큰과 원본 이미지의 보관·삭제 정책
- 최종 확정 결과의 알림·공유 채널
