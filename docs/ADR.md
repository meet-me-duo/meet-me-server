# Architecture Decision Records

## 철학

MVP 출시 속도와 핵심 일정 조율 로직의 정확성을 우선한다. AI는 비정형 입력을 구조화하는 제한된 역할로 사용하고, 중요한 판정은 테스트 가능한 결정론적 서버 로직으로 구현한다. 초기에는 단순하고 운영 가능한 구성을 선택하며, 새로운 외부 의존성은 명확한 제품 가치가 있을 때만 추가한다.

---

### ADR-001: 백엔드 전용 저장소로 운영

**결정**: 이 저장소에서는 백엔드 서버만 개발하고, 프론트엔드는 별도 저장소에서 개발한다.

**이유**: 서버의 도메인 로직, 데이터 모델, 외부 서비스 연동과 API 계약에 작업 범위를 집중하고 프론트엔드의 빌드·배포 주기와 분리하기 위해서다.

**트레이드오프**: API 계약 변경 시 두 저장소 간 조율이 필요하며, 전체 사용자 흐름을 한 저장소에서 통합 검증할 수 없다.

### ADR-002: Spring Boot(Kotlin)와 PostgreSQL 선택

**결정**: 백엔드 애플리케이션은 Spring Boot와 Kotlin으로 구현하고, 주 데이터베이스로 PostgreSQL을 사용한다.

**이유**: 인증, 데이터 접근, 외부 API 연동과 테스트를 위한 Spring 생태계를 활용하면서 Kotlin의 null safety와 간결한 타입 모델을 적용할 수 있다. PostgreSQL은 관계형 데이터 무결성과 일정·좌표 데이터의 확장 가능성을 제공한다.

**트레이드오프**: JVM 기반 애플리케이션의 초기 메모리 사용량과 기동 비용을 감수해야 하며, Kotlin과 Spring의 프록시·영속성 모델을 함께 고려해야 한다.

### ADR-003: Google·Kakao 소셜 로그인 채택

**결정**: MVP 로그인 수단으로 Google과 Kakao 소셜 로그인을 제공하며, 이메일·비밀번호 기반 자체 인증은 구현하지 않는다.

**이유**: 초기 사용자의 가입 마찰을 낮추고 비밀번호 보관과 복구 기능의 구현·운영 부담을 줄이기 위해서다. Google은 범용 계정을, Kakao는 국내 사용자의 접근성을 지원한다.

**트레이드오프**: 두 공급자의 OAuth/OIDC 정책과 장애에 의존하며, 공급자별 사용자 식별자·동의 항목·토큰 처리 차이를 관리해야 한다.

### ADR-004: Redis와 Nginx 도입

**결정**: 백엔드 구성에 Redis와 Nginx를 포함한다. Redis의 구체적인 데이터 책임과 Nginx의 세부 네트워크 책임은 아키텍처 설계에서 확정한다.

**이유**: Redis를 통해 애플리케이션의 휘발성·단기 공유 데이터를 관계형 데이터와 분리할 수 있고, Nginx를 외부 요청과 Spring Boot 애플리케이션 사이의 진입점으로 사용할 수 있다.

**트레이드오프**: PostgreSQL과 애플리케이션 외에 두 컴포넌트를 추가로 구성·관찰·운영해야 하며, Redis 데이터의 일관성 및 장애 복구 정책과 프록시 설정을 별도로 관리해야 한다.

### ADR-005: AWS RDS와 Terraform 채택, 컴퓨팅·레지스트리 결정 유보

**결정**: 로컬 환경에서 개발하고 운영 PostgreSQL은 Amazon RDS로 분리한다. 운영 AWS 인프라는 Terraform으로 관리한다. 애플리케이션 컴퓨팅 환경은 EC2와 ECS 중에서, 컨테이너 이미지 레지스트리는 Docker Hub와 ECR 중에서 추후 결정한다.

**이유**: 애플리케이션과 데이터베이스의 수명주기를 분리하고 인프라 변경을 재현 가능하고 검토 가능한 코드로 관리하되, 운영 복잡도와 비용을 비교한 뒤 컴퓨팅 및 이미지 배포 방식을 선택하기 위해서다.

**트레이드오프**: Terraform 상태와 비밀정보를 안전하게 관리해야 하며, 컴퓨팅과 레지스트리 선택이 확정되기 전까지 네트워크 구성, Nginx·Redis 배치, 배포 파이프라인을 완료할 수 없다.

### ADR-006: 헥사고날 아키텍처 채택

**결정**: 백엔드는 헥사고날 아키텍처로 구현한다. 핵심 도메인과 유스케이스를 내부에 두고, 웹 요청, PostgreSQL·Redis 영속성, AI·OAuth·지도 API 연동을 포트와 어댑터로 분리한다.

**이유**: 일정 매칭 도메인을 Spring과 외부 서비스의 구현 세부사항에서 격리하여 테스트하기 쉽게 만들고, 외부 공급자나 인프라가 변경될 때 핵심 로직의 수정 범위를 줄이기 위해서다.

**트레이드오프**: 단순한 계층형 구조보다 인터페이스와 매핑 코드가 늘어나며, 포트 경계를 과도하게 세분화하면 MVP 개발 속도와 코드 탐색성이 저하될 수 있다.

### ADR-007: Flyway 기반 데이터베이스 마이그레이션

**결정**: PostgreSQL 스키마 변경은 Flyway의 버전 관리 마이그레이션으로 수행하고, 배포 환경에서 ORM의 자동 DDL 변경에 의존하지 않는다.

**이유**: 로컬과 운영 환경에 동일한 스키마 변경 순서를 재현하고, 애플리케이션 버전과 데이터베이스 변경 이력을 함께 검토·추적하기 위해서다.

**트레이드오프**: 스키마 변경마다 명시적인 마이그레이션 파일을 작성·검증해야 하며, 이미 적용된 마이그레이션을 변경하지 않는 운영 규율이 필요하다.

### ADR-008: Google Gemini Flash를 AI 모델 계열로 채택

**결정**: 자연어 조건 구조화와 에브리타임 시간표 이미지 OCR에 Google Gemini Flash 계열 모델을 사용한다. 정확한 stable 모델 ID는 비용과 품질 검증 후 확정한다.

**이유**: 하나의 멀티모달 모델 계열로 텍스트 구조화와 이미지 이해를 처리하고, JSON Schema 기반 Structured Output을 사용하여 서버가 검증할 수 있는 입력을 얻기 위해서다.

**트레이드오프**: Gemini API의 모델 수명주기, 가격, 할당량과 출력 특성에 의존한다. 모델 ID를 확정하기 전에 한국어 조건 파싱과 실제 시간표 이미지에 대한 품질·비용 검증이 필요하다.

### ADR-009: MVP 기본 일정 연동으로 Google Calendar 우선 채택

**결정**: MVP에서는 에브리타임 시간표 캡처본 업로드와 OCR을 제외하고, Google Calendar를 기본 일정 연동으로 우선 제공한다. 사용자는 캘린더 연동을 건너뛸 수 있다. 이 결정은 ADR-008의 에브리타임 시간표 이미지 OCR 채택 부분을 대체하며, 자연어 조건 구조화에 Google Gemini Flash를 사용하는 결정은 유지한다.

**이유**: 구조화된 캘린더 데이터를 먼저 활용하여 이미지 업로드·OCR 검수 흐름과 인식 오류를 MVP에서 제거하고, 일정 조율의 핵심 가치와 결정론적 매칭 검증에 구현 범위를 집중하기 위해서다.

**트레이드오프**: Google 계정과 Calendar 동의 범위에 대한 의존성이 커지고, 에브리타임에만 수업 일정을 관리하는 사용자는 MVP에서 해당 일정을 직접 가져올 수 없다. Calendar 권한, 동기화와 토큰 보관에 대한 별도 보안·실패 처리가 필요하다.

### ADR-010: 단일 모듈의 패키지 기반 헥사고날 구조로 시작

**결정**: MVP 백엔드는 단일 Gradle 모듈로 시작하고 `domain`, `application`, `adapter`, `config` 패키지로 헥사고날 경계를 표현한다. 도메인과 애플리케이션은 외부 어댑터를 의존하지 않으며, 실제 외부 교체 또는 독립 테스트 가치가 있는 경계에만 포트를 둔다.

**이유**: 초기 기능 수와 팀 규모에서 멀티 모듈의 빌드·탐색 비용을 피하면서도 도메인 규칙과 Spring·외부 서비스 구현의 의존성 방향을 명확하게 유지하기 위해서다.

**트레이드오프**: 모듈 수준의 컴파일 격리가 없으므로 패키지 의존성 규율과 아키텍처 테스트가 필요하다. 기능과 팀이 커져 독립 빌드 또는 강한 경계가 필요해지면 멀티 모듈 전환 비용이 발생한다.

### ADR-011: PostgreSQL Transactional Outbox와 Redis Streams로 비동기 작업 전달

**결정**: 자연어 조건 구조화와 일정 후보 생성 같은 비동기 작업은 비즈니스 상태와 Outbox 이벤트를 같은 PostgreSQL 트랜잭션에 기록한 뒤 relay가 Redis Streams에 발행한다. Worker는 Consumer Group으로 작업을 소비하고 처리 성공 후 ACK한다. PostgreSQL을 작업 필요 여부와 처리 상태의 기준으로 유지하며, Redis Pub/Sub은 유실 가능한 실시간 보조 알림 외의 비즈니스 작업 전달에는 사용하지 않는다.

**이유**: 참여자 요청이 Gemini 응답과 매칭 계산을 기다리지 않게 하면서 PostgreSQL 저장과 Redis 발행 사이의 이중 쓰기 실패로 작업이 유실되는 것을 방지하고, 여러 Worker가 작업을 나누어 처리하거나 장애 후 Pending 작업을 복구할 수 있게 하기 위해서다.

**트레이드오프**: Outbox 테이블과 relay, Redis Stream·Consumer Group·Pending 복구·trimming 운영이 추가된다. relay가 Stream 발행 후 Outbox 상태 갱신 전에 중단되면 중복 전달될 수 있으므로 모든 소비자는 이벤트 ID와 비즈니스 상태 전이를 기준으로 멱등해야 한다. Stream 메시지에 포함할 데이터 범위와 보존·실패 정책을 별도로 정해야 한다.

### ADR-012: 자연어 전용 장소 입력과 허용 영역 교집합

**결정**: 참여자는 장소 전용 입력란, 지도 선택 또는 기준 좌표 입력 없이 하나의 자연어 조건만 제출한다. LLM은 위치 표현을 특정 가능한 장소 표현, 개인 기준 이동 제약 또는 미확정 장소로 구조화하며 좌표를 생성하지 않는다. Geo Adapter가 지도 공급자 검색 결과를 하나의 위치로 검증한 표현만 정규화된 장소가 된다. `집`, `회사`, `학교 근처` 같은 개인 기준 표현은 이동 제약으로, `중앙역`처럼 하나로 특정할 수 없는 표현은 미확정 장소로 보존하고 둘 다 장소 좌표를 만들지 않는다. 특정 가능한 장소는 사용자가 명시한 반경 또는 기본 1km 반경의 허용 영역으로 바꾸고, 참여자 내부의 대안은 합집합, 참여자 사이의 조건은 교집합으로 계산한다.

**이유**: 사용자가 대화하듯 입력하는 제품 흐름을 유지하고, 알 수 없는 개인 기준점이나 모호한 지명을 임의 좌표로 바꾸는 오류를 막기 위해서다. 단순히 장소 중심점 사이 거리를 비교하는 대신 허용 영역을 교차하면 `봉천역`과 `서울대입구역`처럼 서로 다른 제안도 중간의 공통 가능 지역으로 계산할 수 있다. LLM의 역할을 의미 구조화로 제한하고 공간 판정을 서버의 테스트 가능한 계산으로 유지한다.

**트레이드오프**: 개인 기준점이 없는 이동 제약이나 모호한 지명만 제시된 조건은 계산 가능한 오프라인 후보를 만들지 못해 온라인 후보로 fallback할 수 있다. 장소 검색 결과의 고유성 기준, 지도 공급자, 원의 교집합에서 실제 장소 후보를 고르는 정책이 추가로 필요하며, 복잡한 이동시간·행정경계·대중교통 접근성은 단순 반경 모델로 정확히 표현되지 않는다.

### ADR-013: 파싱 실패 시 부분 결과와 주최자 한정 원문 공개

**결정**: 제출 버전의 자연어 조건 중 해석 가능한 조건과 독립적으로 유효한 Calendar 불가 시간은 유지하고, 해석할 수 없는 조건만 매칭에서 제외한다. 기술적 재시도를 소진했거나 하나 이상의 최신 제출에 미반영 조건이 있으면 후보 집합을 `PARTIAL`로 표시하고 유효한 입력으로 후보 계산을 계속한다. 제출 전에 공개 가능성을 고지하며, 결과 생성 후 주최자에게만 참여자 표시 이름, 실패 원문과 미반영 사유를 제공한다. 정상 반영된 조건과 미반영 원문은 다른 참여자에게 공개하지 않는다. 별도 실패 알림이나 실패 참여자만을 위한 입력 재개는 MVP에 포함하지 않는다. 주최자는 다른 참여자의 원문을 수정하거나 재처리하지 않으며, 별도 확인 체크박스·모달 없이 `PARTIAL` 표시와 상태가 드러나는 확정 버튼으로 기존의 원클릭 확정 흐름을 유지한다.

**이유**: 알림 채널이 없는 MVP에서 한 사용자의 해석 불가능한 입력 때문에 전체 조율이 중단되는 것을 피하면서, 시스템이 무시한 제약을 주최자가 직접 확인하고 최종 후보를 판단할 수 있게 하기 위해서다. 결과를 `PARTIAL`로 명시하면 모든 조건이 반영됐다는 잘못된 인상을 줄이고, 조건 단위 검증으로 활용 가능한 입력과 Calendar 불가 시간을 보존할 수 있다.

**트레이드오프**: 원래 비공개인 참여자 조건의 일부가 주최자에게 공개되므로 제출 전 고지, 주최자 전용 권한 검증, 안전한 텍스트 렌더링과 로그 제외가 필요하다. 수정·재입력과 추가 확인 단계를 없애 확정 마찰은 낮지만, 주최자가 미반영 원문을 놓치거나 무시된 조건 때문에 부적절한 후보를 확정할 가능성이 남는다.

### ADR-014: IANA Time Zone 기반 시간 모델과 i18n 경계 선도입

**결정**: MVP의 선택 가능한 시간대와 locale은 각각 `Asia/Seoul`, `ko-KR`로 고정한다. 그러나 모든 방은 IANA Time Zone ID를 가지며, 절대 시점은 UTC `Instant`, 자연어 및 반복 조건은 방의 지역 날짜·시간과 Zone ID로 표현하고 후보 생성 시 `ZoneRules`를 적용한다. 방의 후보 탐색 기간은 지역 날짜 반개구간으로 저장하고, 주최자가 시작일과 종료일을 모두 생략하면 방 생성일을 포함한 14일을 서버가 확정하여 저장한다. 이 기간은 자연어 조건을 실제 날짜별 구간으로 확장하고 Calendar 불가 시간을 검증하는 근거 범위다. locale은 BCP 47 태그로 시간대와 분리한다. API 상태·오류 코드, 도메인 값과 후보의 실제 날짜별 구간은 언어 중립적으로 유지한다. 후보 조회 응답은 이 구조화 결과와 Spring MessageSource 템플릿에서 조회 시 생성한 자연어 요약을 함께 제공하며, LLM은 요약 생성에 사용하지 않는다. 반복 조건의 요약은 실제 가능 날짜 수와 완전 제외·일부 축소된 예외 날짜 수를 비교하여 예외가 더 적을 때만 `패턴 + 모든 예외`로 표현하고, 동률 또는 예외가 더 많거나 불규칙한 후보이면 실제 날짜와 시간을 나열한다. 제출 버전에는 입력 locale을 기록하며 AI 결과는 언어 중립적인 서버 스키마로 변환한다.

**이유**: MVP 화면을 한국 사용자에게 단순하게 유지하면서도 이후 시간대 선택과 다국어 지원을 열 때 기존 방·후보·조건 데이터와 API 의미를 마이그레이션하지 않기 위해서다. 고정 offset 대신 IANA Zone ID와 timezone database 규칙을 사용하면 DST gap·overlap과 역사적 offset 변화를 올바르게 계산할 수 있다. 언어 중립 코드·구조화 후보와 메시지 리소스의 분리는 프론트엔드·백엔드가 표시 언어와 비즈니스 상태를 독립적으로 확장하게 하며, 자연어 요약이 결정론적 매칭 결과를 바꾸는 것도 방지한다.

**트레이드오프**: MVP에서 실제 선택지는 하나뿐이어도 Zone ID, locale, UTC 변환과 message bundle 경계를 구현하고 테스트해야 한다. 구조화 후보와 자연어 요약을 함께 제공하고 의미 일치 및 압축 경계 테스트를 유지해야 하므로 응답 모델과 테스트가 늘며, 템플릿 문장은 LLM 생성 문장보다 정형적으로 보일 수 있다. 모든 예외를 숨기지 않기 때문에 일부 결과는 길어질 수 있고 날짜 참조 개수 기반 선택이 번역된 문자열의 실제 길이를 항상 최소화하지는 않는다. 대신 locale과 무관한 결정 규칙과 결과 정확성을 유지한다. timezone database 갱신, DST 경계 테스트와 locale fallback 규칙을 관리해야 하며, 수동 불가 시간 격자의 입력 간격과 추가 언어 품질 및 사용자별 locale 우선순위는 별도로 결정해야 한다.

### ADR-015: 자연어 중심 시간 입력과 선택적 수동 불가 시간 격자

**결정**: 참여자의 기본 입력은 자연어이며 LLM은 `raw_text`를 실제 날짜·요일·시간 구간과 조건으로 구조화한다. Google Calendar 불가 시간과 선택적 수동 격자 입력은 이미 구조화된 별도 입력으로 받아 LLM에 전달하지 않는다. 주최자가 날짜 범위를 명시한 방에서는 수동 격자를 실제 날짜별 불가 시간으로 저장하고, 날짜 범위를 생략해 기본 14일을 적용한 방에서는 월요일부터 일요일까지의 주간 반복 불가 시간으로 저장한 뒤 실제 탐색 범위에 확장한다. 이를 구분하기 위해 방은 계산된 탐색 날짜뿐 아니라 주최자 명시 또는 기본값 적용이라는 범위 출처도 보존한다. 매칭은 자연어 조건, Calendar 불가 시간과 수동 불가 시간의 구간 연산으로 수행하며 고정된 후보 격자로 양자화하지 않는다. 수동 격자의 표시·입력 간격은 별도로 결정한다.

**이유**: 자연어만으로 대부분의 조건을 표현하는 제품 흐름을 유지하면서도 Calendar를 연동하지 않거나 AI 해석과 별개로 확실한 불가 시간을 직접 지정하려는 사용자를 선택적으로 지원하기 위해서다. 격자 셀을 LLM이 채우게 하지 않고 연속 구간으로 합쳐 전달하면 토큰 비용과 파싱 오류를 늘리지 않으며, 명시 날짜와 주간 반복의 의미도 잃지 않는다. 실제 후보 계산을 연속 구간으로 유지하면 수동 UI의 5분·10분 간격이 Calendar 원본 정밀도나 매칭 정확도를 제한하지 않는다.

**트레이드오프**: 제출 계약과 영속 모델이 자연어 조건, Calendar 절대 구간, 실제 날짜형 수동 구간과 주간 반복형 수동 구간으로 늘어난다. 기본 14일 범위와 주간 반복 UI를 구분하려면 날짜 값 외에 범위 출처를 저장해야 하며, 프론트엔드는 방 유형에 맞는 격자와 구간 병합을 구현해야 한다. 선택적 격자는 정확한 보완 수단을 제공하지만 사용자가 다시 표를 채우도록 유도하면 자연어 중심 가치가 약해질 수 있으므로 기본 화면이 아니라 부가 기능으로 유지해야 한다.

### ADR-016: 마감 시 방 전체 입력을 하나의 Gemini 배치로 구조화

**결정**: 참가자의 최초 제출과 수정은 원문 불변 버전과 최신 참조만 PostgreSQL에 저장하며 Gemini를 호출하지 않는다. 입력 수집이 종료되면 그 시점의 참가자별 최신 버전을 하나의 불변 방 전체 제출 배치로 고정하고, 배치당 하나의 논리적 Gemini Structured Output 작업을 비동기로 수행한다. Redis Stream에는 이벤트 ID와 배치 ID만 전달하고 Worker가 PostgreSQL에서 원문을 조회한다. 참가자별 자연어는 최대 500 Unicode 코드 포인트, 배치 합계는 최대 10,000 코드 포인트로 제한하며 초과 입력은 자르지 않고 거부한다. 논리 작업은 최초 호출 1회와 기술적 재시도 최대 3회로 구성하고, 네트워크 오류·timeout·HTTP 429·공급자 5xx에만 Full Jitter 지수 백오프를 적용한다. `Retry-After`가 없을 때 재시도 지연은 각각 `0~1초`, `0~2초`, `0~4초`, 호출별 timeout은 15초, 전체 timeout은 60초다. 재시도 소진 시 모든 자연어를 미반영 처리하고 Calendar·수동 입력만으로 `PARTIAL` 후보를 생성한다.

**이유**: 참가자가 입력을 수정할 때마다 사용하지 않을 AI 호출과 비용이 발생하는 것을 막고, 실제 매칭에 사용할 종료 시점 스냅샷만 한 번 구조화하여 사용자가 의도한 모임당 단일 배치 처리와 비용 추적 단위를 일치시키기 위해서다. Outbox 이벤트와 배치 스냅샷을 종료 트랜잭션에 함께 기록하면 어떤 버전을 처리해야 하는지 명확하며 Redis에 개인정보성 원문을 복제하지 않아도 된다. 제한된 기술적 재시도와 지터는 일시 장애 복구 가능성을 높이면서 동시 재시도 폭주를 줄인다.

**트레이드오프**: 참가자별 호출보다 요청과 응답이 커지고 하나의 공급자 장애가 방 전체 자연어 처리에 영향을 준다. 재시도하면 전체 배치를 다시 호출하므로 비용이 중복될 수 있으며, 재시도 소진 시 Calendar·수동 입력만 반영된 부분 결과가 된다. 입력 길이 제한과 향후 최대 참여자 수 제한이 필요하고, 응답에서 참가자별 불투명 참조값과 개수를 엄격히 검증해야 한다. 마감 전에는 자연어 구조화 오류를 미리 발견할 수 없으며, 운영자는 배치 실패와 Worker poison message를 구분해 관찰해야 한다.

### ADR-017: Grafana Cloud 관리형 관측성과 참조형 Redis DLQ 채택

**결정**: MVP 운영 관측성은 Spring Boot Actuator·Micrometer의 Prometheus 지표와 표준 출력 JSON 로그를 Grafana Alloy가 수집하여 Grafana Cloud Metrics 및 Loki로 전송하고, Grafana-managed Alerting으로 운영 알림을 평가하는 구성으로 한다. Grafana·Loki·Prometheus는 자체 운영하지 않으며 분산 tracing 저장소는 MVP에 포함하지 않는다. PostgreSQL을 비동기 작업 상태와 실패 이력의 최종 기준으로 유지한다. Gemini 기술적 재시도 소진은 Calendar·수동 입력 기반 `PARTIAL` 결과로 종결하고 Stream 메시지를 ACK하며 DLQ에 넣지 않는다. Redis DLQ는 반복 Worker crash, 역직렬화 실패, 존재하지 않는 참조와 불변식 위반 같은 poison message만 대상으로 한다. 첫 전달을 포함해 동일 메시지의 처리가 총 5회 실패하면 PostgreSQL에 영구 실패 상태를 기록한 뒤 DLQ로 옮기며, DLQ에는 이벤트 ID·방 전체 제출 배치 ID·실패 분류·전달 횟수만 저장한다. Redis 메시지 전달 횟수는 Gemini API 재시도 횟수와 별도로 센다. 원문과 사용자·Calendar 데이터는 로그, metric label과 DLQ에 저장하지 않는다.

**이유**: 초기 팀이 로그 저장소, 지표 저장소와 알림 시스템 자체를 운영하는 부담 없이 Gemini 배치 실패, Outbox·Redis 적체와 Worker 장애를 능동적으로 탐지하기 위해서다. 비즈니스 정책에 따라 부분 결과까지 생성한 공급자 실패와 실제로 처리되지 않은 poison message를 구분하면 정상 종결 작업의 불필요한 재호출과 중복 비용을 막을 수 있다. PostgreSQL에 영구 상태를 남기고 Redis DLQ에는 참조만 저장하면 Redis 유실이나 trimming에도 작업 상태를 복구할 수 있고 민감한 원문의 복제를 피할 수 있다.

**트레이드오프**: Grafana Cloud 계정, 전송 자격 증명, 외부 네트워크와 공급자 가용성에 의존하며 관측 데이터가 외부 관리형 서비스로 전송된다. Alloy 런타임과 설정, telemetry 사용량·label cardinality·보존 정책을 관리해야 하고 무료 허용량을 넘으면 비용이 발생할 수 있다. PostgreSQL 실패 상태와 Redis DLQ를 함께 유지하므로 전이·ACK·재처리의 멱등성 테스트가 필요하다. 총 5회는 일시적인 Worker 장애를 복구할 여지를 주지만 구조적으로 잘못된 메시지도 반복 처리하며, 장기 인프라 장애에서는 복구 전에 DLQ로 격리될 수 있다. 분산 tracing을 제외하여 초기 구성은 단순하지만 복잡한 비동기 경로의 원인 분석에는 지표·로그 상관관계에 의존한다. Pending 회수 대기시간, DLQ 보존 기간, 재처리 방식과 알림 연락 채널·임계값은 별도로 확정해야 한다.

### ADR-018: Gemini 기술적 실패를 분석 지연으로 보존하고 방 단위 재분석 허용

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: 방 전체 Gemini 논리 작업의 제한된 기술적 재시도가 소진되면 Calendar·수동 입력만으로 `PARTIAL` 후보를 만들지 않고 입력과 고정 배치를 PostgreSQL에 보존한 채 방을 `ANALYSIS_DELAYED`로 전이한다. Worker는 실패 분류와 호출 시도 메타데이터를 기록하고 원본 Stream 메시지를 ACK하며 Redis DLQ에는 넣지 않는다. 프론트엔드는 무기한 로딩을 종료하고 입력 저장 완료와 분석 지연 상태를 표시한다. 인증된 주최자는 참가자의 재입력 없이 같은 고정 배치에 대한 방 단위 분석을 멱등하게 다시 요청할 수 있다. Gemini 응답이 성공한 뒤 개별 입력이 의미·스키마·도메인 검증에 실패한 경우에는 기존처럼 유효한 입력으로 `PARTIAL` 후보를 만들고 해당 실패 원문만 주최자에게 공개한다. 기술적 전체 장애에서는 모든 원문을 주최자에게 공개하지 않는다. 자동 지연 재시도 여부와 상한은 후속 결정으로 남긴다. 이 결정은 ADR-013, ADR-016, ADR-017의 기술적 재시도 소진 시 즉시 `PARTIAL` 처리하는 부분을 대체하며 의미 검증 실패와 poison message DLQ 결정은 유지한다.

**이유**: 외부 공급자의 일시·장기 장애가 모든 참여자 자연어 조건을 무시한 후보로 굳어지는 것을 막고, 이미 서버에 안전하게 저장된 입력을 참가자가 다시 작성하지 않아도 장애 복구 후 온전한 결과를 만들기 위해서다. 기술적 전체 장애와 의미상 해석할 수 없는 일부 입력을 분리하면 `PARTIAL`의 의미와 블라인드 입력 원칙도 보존된다.

**트레이드오프**: 장애 중 즉시 제공할 수 있는 Calendar·수동 입력 기반 후보를 포기하므로 결과 도착이 늦어지고 주최자의 재요청 또는 향후 자동 재시도 정책이 필요하다. `ANALYSIS_DELAYED` 상태, 상태 조회·재분석 API와 멱등성 제어가 추가된다. 대신 잘못된 부분 결과 확정과 참여자 재입력 부담을 피하고, Gemini 복구 뒤 같은 스냅샷을 재현 가능하게 처리할 수 있다.

### ADR-019: 주최자 로그인 필수와 게스트 참여 허용

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: 방 생성과 주최자 전용 명령은 Google 또는 Kakao로 로그인한 서비스 사용자만 수행한다. 일반 참여자는 서비스 로그인 없이 공유 링크로 방에 참여하고 조건을 제출할 수 있다. 로그인 여부와 관계없이 각 참여자는 서버가 인정하는 본인 증명으로 자신의 최신 제출 Payload를 조회·수정할 수 있지만 다른 참여자의 입력은 조회할 수 없다. 공유 초대 링크 자체는 제출 소유권 증명이 아니다. 주최자도 정상 입력과 `ANALYSIS_DELAYED` 상태의 타인 원문을 조회할 수 없으며, Gemini 응답 성공 후 의미 검증에 실패한 원문만 ADR-013의 예외에 따라 볼 수 있다. 게스트 본인 증명의 구체적인 전달·저장 방식은 ADR-020에서 확정하며 수명, 기기 변경과 복구 정책은 후속 결정으로 남긴다.

**이유**: 방을 만드는 주체와 재분석·최종 확정 권한은 지속적인 서비스 계정에 연결하면서도, 초대받은 참여자에게 로그인 마찰을 강제하지 않기 위해서다. 본인 최신 입력 조회 API를 제공하면 새로고침이나 분석 지연 뒤에도 서버에 저장된 값을 복원할 수 있다.

**트레이드오프**: 게스트 참여가 쉬운 대신 브라우저 변경, 자격 증명 분실, 공유 기기와 링크 유출을 다루는 별도 소유권·복구 설계가 필요하다. 로그인 계정만 사용하는 모델보다 권한 테스트와 만료·회수 정책이 복잡해지고, Calendar OAuth 동의와 meet-me 서비스 로그인도 별도 개념으로 명확히 분리해야 한다.

### ADR-020: 게스트 참여자 소유권에 Secure HttpOnly 불투명 자격 증명 사용

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: 서버는 비로그인 참여가 성립할 때 암호학적으로 안전한 난수로 추측하기 어려운 불투명 게스트 자격 증명을 발급하고 `Secure HttpOnly` 쿠키의 `Set-Cookie`로만 전달한다. 이 값은 bearer 자격 증명이므로 응답 JSON, URL, JavaScript가 읽는 `localStorage`·`sessionStorage`, 로그, 지표와 Redis 메시지에 포함하지 않는다. PostgreSQL에는 자격 증명 원문 대신 단방향 해시와 만료·회수 상태만 저장한다. 이후 본인 최신 제출 조회·수정 요청은 쿠키를 자동 전송하며, 서버는 해시 비교와 참여자 소유권 검증에 성공한 요청만 허용한다. 공유 초대 링크나 쿠키가 없거나 유효하지 않은 요청에는 기존 제출 소유권을 부여하지 않는다. 자격 증명의 범위는 ADR-021에서 확정하며 cookie `SameSite`·`Domain`·`Path`·`Max-Age`, digest 알고리즘, 회전·회수, CSRF 방어와 복구 정책은 후속 설계에서 확정한다.

**이유**: 프론트엔드 JavaScript가 게스트 자격 증명을 직접 보관하지 않아 XSS 발생 시 토큰 탈취 면적을 줄이면서, 같은 브라우저에서는 로그인 없이 본인 입력을 자연스럽게 다시 조회하고 수정하게 하기 위해서다. 고엔트로피 원문을 서버에도 저장하지 않으면 데이터베이스가 노출되더라도 즉시 사용할 수 있는 게스트 bearer 자격 증명의 유출을 줄일 수 있다.

**트레이드오프**: 브라우저가 쿠키를 삭제하거나 시크릿 세션이 끝나고 다른 기기에서 접속하면 자동으로 소유권을 복구할 수 없다. 쿠키가 자동 전송되므로 변경 API에 별도 CSRF 방어가 필요하고, 프론트엔드와 API의 origin 구성에 따라 `SameSite`·CORS·credential 설정이 달라진다. `localStorage` 방식보다 프론트엔드 디버깅은 덜 직접적이며, 여러 방 참여를 하나의 게스트 세션으로 묶을지 방별 자격 증명으로 격리할지도 구현 전에 선택해야 한다.

### ADR-021: 하나의 게스트 브라우저 세션으로 여러 방 참여 소유

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: `Secure HttpOnly` 게스트 자격 증명 하나를 브라우저 단위 세션으로 취급하고, 동일한 유효 세션을 여러 방의 참여자 소유권에 재사용한다. PostgreSQL은 게스트 브라우저 세션과 방별 참여자를 분리하여 저장하고 하나의 세션에서 여러 참여자로 이어지는 일대다 관계를 허용한다. 다만 `(guest_browser_session_id, room_id)` 조합은 유일해야 하므로 같은 브라우저 세션은 한 방에서 최대 한 명의 게스트 참여자만 소유한다. 유효한 세션이 같은 방의 참여 링크를 다시 열면 새 참여자를 생성하지 않고 기존 참여자를 식별한다. 이 결정은 ADR-020에서 남긴 자격 증명 범위 TBD를 확정한다.

**이유**: 방마다 쿠키를 발급하여 브라우저 cookie 개수·경로·정리 정책이 복잡해지는 것을 피하고, 사용자가 같은 브라우저에서 참여한 여러 방의 자기 입력을 로그인 없이 자연스럽게 복원하기 위해서다. 한 세션이 같은 방의 여러 참여자를 소유하지 않게 해야 `내 입력` 조회의 대상이 단일하게 유지되고, 같은 기기를 쓰는 참여자 사이의 블라인드 입력도 보호할 수 있다.

**트레이드오프**: 자격 증명 하나가 유출되면 해당 브라우저 세션이 참여한 여러 방의 입력에 영향이 확대된다. 하나의 브라우저 프로필을 여러 사람이 공유하면서 같은 방에 각각 참여하는 흐름은 지원할 수 없으므로 별도 프로필·시크릿 세션·로그인 또는 향후 세션 전환 UX가 필요하다. 방별 쿠키보다 저장과 브라우저 관리는 단순하지만 세션 회전·회수 시 여러 방의 소유권에 미치는 영향을 함께 처리해야 한다.

### ADR-022: Google Calendar 연동을 로그인 사용자로 제한

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: Google Calendar OAuth 시작·콜백과 grant 저장은 meet-me에 로그인한 참여자에게만 허용한다. 주최자 외 참여자는 로그인 없이 게스트로 전체 조율 흐름을 이용할 수 있지만, 이 경우 Calendar 연동을 제공하지 않고 해당 방에만 귀속되는 meet-me 시간 격자를 사용한다. 게스트의 시간 격자 입력은 계정 프로필이나 다른 방에 누적·재사용하지 않는다. 로그인한 참여자도 Calendar를 건너뛰거나 방 전용 격자로 보완할 수 있다. 이 결정은 ADR-009의 Calendar 연동 대상 범위를 인증된 서비스 사용자로 제한한다.

**이유**: OAuth grant와 Calendar 토큰을 지속적인 서비스 사용자에게만 연결하여 게스트 브라우저 세션의 만료·분실·공유 문제와 민감한 장기 토큰 수명주기를 분리하기 위해서다. 로그인하지 않으려는 참여자에게는 기존 일정 서비스처럼 방 전용 시간 입력을 제공하여 조율 참여 자체는 막지 않는다.

**트레이드오프**: Google Calendar 일정이 이미 있는 게스트도 자동 불가 시간 수집을 사용하려면 meet-me 로그인을 추가로 해야 한다. 로그인하지 않으면 방마다 시간을 직접 입력해야 하므로 반복 부담과 누락 가능성이 커진다. 대신 게스트 자격 증명에 Calendar grant를 연결하는 복잡도와 토큰 유출 범위를 줄이고, 일회성 참여라는 제품 경계를 명확하게 유지한다.

### ADR-023: 수동 일정 입력은 가능 시간 선택, Calendar 입력은 불가 시간 차감

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: 비로그인 게스트와 Google Calendar를 사용하지 않는 로그인 참여자는 `MANUAL_AVAILABILITY` 모드에서 웬투밋처럼 방 전용 격자의 가능한 시간을 선택한다. Google Calendar를 연동한 로그인 참여자는 `CALENDAR` 모드에서 공급자가 제공한 절대 불가 시간을 사용하며 필요하면 별도의 추가 불가 시간으로 보완한다. 두 모드의 격자 입력은 LLM에 전달하지 않고 계정 프로필이나 다른 방에 재사용하지 않는다. 매칭에서는 자연어 시간 조건이 만든 기준 구간과 수동 가능 시간을 교차하고, Calendar 모드에서는 기준 구간에서 Calendar·추가 불가 시간의 합집합을 차감한다. 자연어 시간 조건이 없거나 의미 검증에서 제외되면 탐색 범위 전체를 중립적인 기준 구간으로 사용한다. 이 결정은 ADR-015의 모든 수동 격자를 불가 시간으로 저장하는 부분을 대체하며, 실제 날짜형·주간 반복형 구분과 연속 구간 계산 결정은 유지한다. `MANUAL_AVAILABILITY`의 빈 선택 의미는 후속 결정으로 남긴다.

**이유**: Calendar가 없는 참여자에게 선택하지 않은 시간을 모두 가능하다고 간주하는 위험을 피하고, 기존 일정 조율 도구와 같은 명확한 가능 시간 입력 경험을 제공하기 위해서다. 반면 Calendar 사용자는 이미 공급자가 불가 시간을 제공하므로 가능한 시간을 다시 전부 칠하지 않고 예외만 추가하는 편이 입력 부담이 작다.

**트레이드오프**: 사용자에게는 각 입력 모드에 자연스러운 UX를 제공하지만 API와 도메인은 가능 시간 교차와 불가 시간 차감이라는 두 정형 입력 의미를 지원해야 한다. 모드와 맞지 않는 필드 조합을 거부하고 두 경로를 별도로 테스트해야 하며, Calendar 사용 여부를 바꿀 때 기존 격자 값의 폐기·전환 정책도 필요하다. 수동 가능 시간 선택은 거짓 가능성을 줄이는 대신 가능한 시간이 넓은 참여자의 입력량을 늘릴 수 있다.

### ADR-024: 자연어와 수동 가능 시간을 독립적인 선택 입력으로 허용

**상태**: Accepted  
**날짜**: 2026-09-07  
**결정**: 자연어와 방 전용 수동 가능 시간 격자를 각각 선택 입력으로 취급한다. `MANUAL_AVAILABILITY` 제출은 공백이 아닌 자연어 또는 하나 이상의 수동 가능 시간 구간 중 적어도 하나를 포함해야 한다. 자연어만 제출하면 빈 `manual_available_times`를 부가 슬롯 제약 없음으로 해석하고 자연어 기준 구간을 그대로 사용한다. 수동 가능 시간만 제출하면 탐색 범위 전체를 중립적인 자연어 기준 구간으로 삼아 선택 구간과 교차한다. 입력 수집 종료 시 자연어가 하나 이상인 경우에만 자연어가 있는 항목으로 방 단위 Gemini 논리 작업 하나를 만들며, 자연어 없는 참여자는 AI 요청에서 제외하되 정형 일정 입력은 매칭에 포함한다. 전원이 합의된 정형 일정 입력만 제출했으면 Gemini를 호출하지 않고 결정론적 매칭을 시작한다. `CALENDAR` 모드에서 Calendar 스냅샷만으로 자연어 생략을 허용할지는 별도 결정으로 남긴다. 이 결정은 ADR-015의 자연어가 기본 입력이라는 부분을 자연어 중심 UX 원칙으로만 유지하고 `MANUAL_AVAILABILITY`에서 항상 필수라는 해석은 대체하며, ADR-023의 빈 수동 가능 시간 의미 TBD를 확정한다.

**이유**: 시간 격자는 자연어 경험을 보완하는 부가 기능이므로 사용자가 사용하지 않았다는 이유로 제출을 막거나 `가능 시간 없음`으로 오해해서는 안 된다. 반대로 사용자가 격자에 충분한 가능 시간을 명시했다면 의미 없는 자연어를 강제로 작성하게 할 필요가 없다. AI가 해석할 원문이 없는 배치는 외부 호출 없이 동일한 정형 데이터로 계산하는 편이 비용과 실패 가능성을 줄인다.

**트레이드오프**: 제출 유효성 검증이 단순한 자연어 필수 규칙에서 모드별 조건 규칙으로 바뀌고, nullable 원문과 자연어가 없는 참여자·방을 처리하는 상태 전이 및 테스트가 추가된다. 빈 수동 배열을 `가능 시간 없음`으로 표현할 수 없으므로 실제로 가능한 시간이 전혀 없는 사용자를 위한 별도 표현이나 UX가 필요할 수 있다. 대신 슬롯을 숨은 부가 기능으로 유지하면서 자연어 전용·슬롯 전용 흐름을 지원하고 불필요한 Gemini 비용과 장애 경로를 제거한다. Calendar 전용 제출은 아직 미정이므로 해당 계약 구현 전에 추가 선택이 필요하다.

### ADR-025: Calendar 연결과 방별 적용을 분리하고 ON을 가용성 동의로 취급

**상태**: Accepted  
**날짜**: 2026-09-08  
**결정**: meet-me에 로그인한 개인만 자신의 Google Calendar를 계정에 연결하고 일정을 조회할 수 있다. 개인 계정의 연결·조회 상태와 현재 참여 중인 방의 매칭 적용 상태를 분리한다. Calendar를 연결한 참여자 본인이 현재 방에서 사용을 ON/OFF하며 주최자나 다른 참여자는 대신 변경할 수 없다. 최신 제출의 `schedule_input_mode=CALENDAR`를 ON으로, `MANUAL_AVAILABILITY`를 OFF로 취급하며 별도 확인 boolean은 저장하거나 API에서 요구하지 않는다. ON이면 자연어 없이도 유효한 Calendar 스냅샷만으로 제출할 수 있고, Calendar 불가 일정과 선택적인 추가 불가 시간을 제외한 탐색 범위 전체를 해당 참여자가 허용한 기준 범위로 본다. 이 범위는 다른 참여자의 일정과 교차하여 좁힌다. OFF이면 이미 불러온 Calendar 데이터가 있어도 현재 방의 매칭에서 무시한다. 입력 수집 중 ON/OFF 변경은 새 제출 버전으로 저장하고 종료 시점의 최신 모드만 사용한다. 프론트엔드는 참여자·방별 최초 ON 전환 시 "Calendar에 등록된 불가 일정 외 시간은 모두 후보가 될 수 있다"는 확인 팝업을 한 번만 표시하며, 팝업 표시 이력은 프론트엔드 책임이다. 이 결정은 ADR-024의 Calendar 전용 제출 TBD를 확정한다.

**이유**: 사용자가 Calendar 권한을 부여했거나 일정을 조회했다는 사실만으로 모든 방에 일정을 강제로 적용하지 않으면서, 특정 방에서 ON한 경우에는 추가 자연어 입력 없이도 자신의 의사를 명확하게 표현하게 하기 위해서다. 한 번의 확인으로 빈 Calendar 시간이 단순한 데이터 부재가 아니라 약속 후보로 사용 가능한 시간이라는 의미를 사용자에게 알리고, 이후 후보는 나머지 참여자의 제약으로 자연스럽게 좁힐 수 있다.

**트레이드오프**: Calendar ON 사용자가 자연어로 생활 시간대를 제한하지 않으면 심야·이른 아침을 포함한 탐색 범위도 후보가 될 수 있으나, 이는 확인 팝업에서 동의한 의미다. 연결 상태와 방별 적용 상태, ON/OFF 수정 버전을 분리해 테스트해야 하고 프론트엔드는 참여자·방별 1회 팝업 표시 이력을 관리해야 한다. 백엔드가 별도 확인 필드를 저장하지 않으므로 팝업이 실제 표시되었는지는 서버에서 감사할 수 없지만 API와 도메인 상태가 단순해지고 반복 확인 마찰을 피할 수 있다.

### ADR-026: Calendar ON 제출 시점의 일정을 불변 스냅샷으로 고정

**상태**: Accepted  
**날짜**: 2026-09-08  
**결정**: Calendar ON 제출과 수정은 요청 접수 시점에 Google Calendar를 조회하고 정규화된 불가 시간과 조회 완료 시각을 해당 불변 제출 버전에 함께 저장한다. 화면 미리보기나 이전 제출의 조회 결과를 새 제출의 기준으로 재사용하지 않는다. Calendar 조회에 성공해 유효한 스냅샷을 저장한 경우에만 Calendar ON 제출을 접수한다. 입력 수집 종료와 방 전체 배치 고정 시에는 Google Calendar를 다시 호출하지 않고, 종료 시점의 참가자별 최신 제출 버전에 저장된 스냅샷만 매칭에 사용한다.

**이유**: 참가자가 제출할 때 확인한 일정과 실제 매칭 입력을 일치시키고, 동일한 제출 배치로 결과를 재현할 수 있게 하기 위해서다. 방 마감 트랜잭션과 Google Calendar 가용성을 분리하면 마지막 참가자 요청이나 데드라인 처리 중 외부 장애로 전체 방 마감이 지연되는 것도 피할 수 있다.

**트레이드오프**: 제출 뒤 Google Calendar에 추가되거나 변경된 일정은 자동으로 최신 배치에 반영되지 않는다. 최신 반영이 필요하면 입력 수집이 열려 있을 때 Calendar ON 상태로 다시 제출하여 새 스냅샷 버전을 만들어야 한다. Calendar ON 제출 자체는 외부 조회 지연과 실패의 영향을 받으며, 실패 시 Calendar를 OFF하고 다른 유효 입력으로 제출하는 흐름과 정확한 오류 UX를 별도로 설계해야 한다.

### ADR-027: 방 수집·조율 작업·후보 품질·최종 확정 상태 분리

**상태**: Accepted  
**날짜**: 2026-09-08  
**결정**: 입력 수집, 비동기 조율 작업, 후보 집합 품질과 최종 확정을 하나의 방 상태 enum에 합치지 않는다. 방은 `COLLECTING`과 `CLOSED`의 수집 상태 및 마감 원인을 가지고, 고정 제출 배치는 `QUEUED`, `STRUCTURING`, `MATCHING`, `COMPLETED`, `ANALYSIS_DELAYED`, `DEAD_LETTERED`의 독립적인 조율 작업 상태를 가진다. 자연어가 없는 배치는 구조화 단계를 건너뛴다. 후보 집합은 `COMPLETE` 또는 `PARTIAL` 품질을 가지며 최종 확정은 선택한 후보 참조와 확정 시각으로 표현한다. PostgreSQL의 이 상태들이 기준이며, API는 이를 조합해 `COLLECTING`, `ANALYZING`, `ANALYSIS_DELAYED`, `READY`, `READY_WITH_WARNINGS`, `INSUFFICIENT_PARTICIPANTS`, `CONFIRMED` 중 하나의 공개 진행 상태를 계산하여 제공한다. 공개 진행 상태 자체는 별도의 영구 기준 상태로 중복 저장하지 않는다. 재분석은 같은 불변 제출 배치의 조율 작업만 다시 진행하고 `CLOSED`인 입력 수집을 다시 열지 않는다.

**이유**: 입력 수집 가능 여부, Redis Streams를 거치는 비동기 작업의 진행·실패, 부분 결과 여부와 주최자의 최종 선택은 서로 다른 생명주기를 가진다. 이를 분리하면 Gemini 장애 후 재분석이나 중복 메시지 처리 중에도 마감된 입력을 다시 열지 않고, `ANALYSIS_DELAYED`라는 작업 실패와 `PARTIAL`이라는 결과 품질을 명확히 구분할 수 있다. 클라이언트에는 계산된 단일 진행 상태를 제공하여 내부 모델의 복잡성을 노출하지 않는다.

**트레이드오프**: 단일 `RoomStatus`보다 상태 타입과 영속 필드가 늘고 허용 가능한 조합을 검증하는 불변식·동시성 테스트가 필요하다. 조회할 때 공개 진행 상태를 계산해야 하며 목록 필터링이나 집계 쿼리가 복잡해질 수 있다. 대신 파생 상태를 중복 저장하지 않아 내부 상태와 공개 상태가 어긋나는 이중 기준을 피하고, 각 생명주기를 독립적으로 변경·복구할 수 있다.

### ADR-028: Komapper JDBC와 영속 Record 분리 채택

**상태**: Accepted  
**날짜**: 2026-09-08  
**결정**: PostgreSQL 데이터 접근에 Komapper JDBC를 사용하고 MVP에서 R2DBC를 혼용하지 않는다. 도메인 Aggregate·Entity·Value Object에는 Komapper나 Spring 애너테이션을 붙이지 않는다. PostgreSQL 테이블 행은 `adapter.output.persistence`의 별도 불변 `*Record`로 표현하고, Komapper의 `@KomapperEntityDef` 매핑 정의와 KSP 생성 메타모델도 같은 어댑터 경계에 둔다. Web DTO, 외부 공급자 DTO, Application Command·Result, 도메인 모델과 영속 `Record`는 각 경계의 책임에 맞게 분리하고 명시적인 Mapper로 변환한다. Application의 outbound persistence port에는 Komapper 타입을 노출하지 않는다. Flyway SQL을 스키마의 기준으로 유지하며 Komapper 스키마 생성 기능으로 운영 스키마를 변경하지 않는다. 원자적 유스케이스의 트랜잭션 경계는 Application 서비스의 공개 메서드에 Spring `@Transactional`을 적용해 선언하고 Komapper JDBC 작업이 같은 Spring 관리 트랜잭션에 참여하게 한다. Domain에는 Spring 트랜잭션 타입을 노출하지 않는다. 로컬·통합 테스트 PostgreSQL 구성은 후속 결정으로 남긴다.

**이유**: Komapper는 Kotlin 불변 `data class`와 value class, 컴파일 시점 KSP 메타모델 및 Spring 관리 트랜잭션을 지원하면서 JPA의 프록시·지연 로딩·dirty checking 없이 쿼리와 갱신을 명시적으로 표현한다. 이는 방 마감, 제출 버전 고정, Outbox 기록과 같은 트랜잭션을 분명하게 만들고 도메인 모델을 영속 기술에서 격리하려는 패키지 기반 헥사고날 구조에 맞는다. 현재 Spring MVC 기반 애플리케이션에는 JDBC가 자연스럽고 R2DBC를 함께 도입할 제품상 이점이 없다.

**트레이드오프**: JPA보다 생태계와 팀 경험이 작고 KSP 플러그인·생성 메타모델을 빌드에 추가해야 한다. 도메인 모델과 `Record`를 분리하므로 필드가 유사한 클래스와 Mapper 코드가 늘고, Flyway 스키마 변경 시 SQL·Record·매핑 정의·Mapper를 함께 갱신해야 한다. 자동 관계 탐색과 dirty checking을 사용하지 않는 대신 조인·잠금·갱신 SQL 의도를 직접 관리해야 하며, Komapper 버전 업그레이드 시 KSP 및 Kotlin 호환성을 검증해야 한다. Application 계층이 Spring의 `@Transactional` 애너테이션에 의존하지만 Domain은 순수하게 유지된다. 트랜잭션 데코레이터보다 구조와 탐색은 단순한 대신 Spring을 다른 프레임워크로 교체하려면 Application 서비스의 애너테이션을 변경해야 한다.

### ADR-029: JWT Access와 Redis TTL 기반 불투명 Refresh Token 채택

**상태**: Accepted  
**날짜**: 2026-09-08  
**결정**: meet-me 서비스 인증은 15분 수명의 JWT Access Token과 암호학적으로 안전한 불투명 Refresh Token까지만 구현한다. Access Token은 로그인·갱신 response body로 발급하고 이후 요청의 `Authorization: Bearer` 헤더에서 받으며, 프론트엔드의 영구 브라우저 저장소에는 보관하지 않는다. 각 요청은 Access Token의 서명과 만료를 검증하되 Redis 조회를 요구하지 않는다. Refresh Token은 `Set-Cookie`의 `Secure HttpOnly` 쿠키로만 전달하고 원문을 서버에 저장하지 않으며, 해시, 사용자·토큰 패밀리 참조, 회전·폐기 상태를 Redis TTL로 관리한다. Refresh Token의 미사용 TTL은 14일이고 토큰 패밀리의 절대 수명은 최초 로그인부터 30일이다. 갱신할 때 기존 토큰을 폐기하고 새 토큰의 미사용 TTL을 시작하되 패밀리의 절대 만료를 연장하지 않는다. 이미 폐기된 토큰의 재사용을 감지하면 같은 토큰 패밀리를 폐기한다. 로그아웃은 해당 Refresh 상태를 폐기하지만 이미 발급된 Access Token은 최대 15분 동안 유효할 수 있다. Redis 장애 중에는 갱신이 실패하고 Redis 데이터 유실 시 사용자가 다시 로그인해야 하며, 영구 사용자·방 데이터는 PostgreSQL에 남는다. Google·Kakao 공급자 Refresh Token은 meet-me Refresh Token과 분리하여 PostgreSQL에 암호화해 보관한다. JWT 서명·키 회전과 Refresh cookie·CSRF 정책은 ADR-030, 현재·전체 기기 로그아웃 범위는 ADR-031에서 확정하며 공급자 토큰 암호화 키 관리는 후속 결정으로 남긴다.

**이유**: 짧은 Access JWT로 일반 API 요청의 Redis 의존성을 피하면서, 장기 권한을 가진 Refresh Token은 서버 상태와 TTL을 통해 즉시 폐기·회전하고 탈취 재사용을 탐지하기 위해서다. Redis의 휘발성은 로그인 세션 유실과 재로그인으로 복구할 수 있어 영구 비즈니스 데이터 기준을 PostgreSQL에 유지하는 원칙과 충돌하지 않는다. 공급자 토큰은 Calendar 연동의 지속성에 필요하므로 Redis 유실로 사라지는 서비스 Refresh 세션과 다른 수명주기로 관리한다.

**트레이드오프**: Refresh 요청과 로그아웃은 Redis 가용성에 의존하고 Redis 데이터가 유실되면 모든 사용자가 다시 로그인해야 한다. Access Token denylist를 두지 않으므로 로그아웃이나 Refresh 재사용 탐지 후에도 이미 발급된 Access Token은 최대 15분 동안 사용할 수 있다. 미사용 14일은 장기 방치된 세션을 줄이고 절대 30일은 회전만으로 무기한 로그인되는 것을 막지만, 활동 중인 사용자도 30일마다 소셜 로그인을 다시 해야 한다. Access Token을 body로 전달하면 프론트엔드 JavaScript가 이를 다뤄야 하므로 XSS 방어와 메모리 보관 원칙이 필요하고, Refresh 쿠키는 XSS 노출을 줄이는 대신 CSRF 방어와 CORS credential 설정이 필요하다. Refresh Token 회전의 동시 요청, 토큰 패밀리 폐기와 재사용 탐지 로직이 추가되며 공급자 Refresh Token을 위해 PostgreSQL 컬럼 암호화와 별도 키 관리가 필요하다.

### ADR-030: RS256 JWT와 same-site Refresh 쿠키 방어 채택

**상태**: Accepted  
**날짜**: 2026-09-08  
**결정**: meet-me Access Token은 RS256으로 서명한다. JWT 헤더의 `kid`로 검증 공개키를 선택하고 현재 private key 하나만 서명에 사용하며, 키 교체 중에는 이전 public key를 이미 발급된 Access Token의 15분 수명과 허용 clock skew가 모두 지날 때까지 검증 키 집합에 유지한다. Private key는 저장소·컨테이너 이미지·로그에 넣지 않고 환경별 비밀 저장소에서 주입한다. 운영 프론트엔드와 API는 같은 상위 사이트의 서브도메인에 배치한다. Refresh Token은 `Secure HttpOnly; SameSite=Lax; Path=/api/auth` 쿠키로만 전달하고 `Domain`을 생략하여 API 호스트 전용으로 제한한다. 쿠키 `Max-Age`는 미사용 14일과 토큰 패밀리의 남은 절대 수명 중 짧은 값으로 설정한다. Refresh와 로그아웃처럼 이 쿠키로 권한을 행사하는 상태 변경 요청은 명시적 프론트엔드 Origin과 정확히 일치해야 하며, 서버는 Origin 누락·불일치와 wildcard credential CORS를 거부한다. 이 경계에서는 별도 synchronizer 또는 double-submit CSRF token을 추가하지 않는다. 게스트 자격 증명 cookie 정책은 별도 결정으로 유지한다.

**이유**: 비대칭 서명을 사용하면 토큰 검증에 필요한 public key와 토큰을 생성할 수 있는 private key를 분리할 수 있고, `kid` 기반 검증 키 집합은 짧은 Access Token 수명 동안 무중단 키 교체를 가능하게 한다. Refresh Token은 브라우저가 자동으로 전송하므로 XSS 노출을 줄이는 `HttpOnly`만으로는 충분하지 않다. 같은 사이트의 서브도메인 배치, `SameSite=Lax`와 엄격한 Origin 검증을 결합하면 일반적인 교차 사이트 요청을 차단하면서 별도 CSRF token 교환 없이 브라우저 로그인 갱신 흐름을 유지할 수 있다. API 호스트 전용 cookie와 좁은 Path는 쿠키가 불필요한 호스트·경로로 전송되는 범위를 줄인다.

**트레이드오프**: HS256보다 private/public key 배포와 `kid` 수명주기 관리가 복잡하고, 실제 운영 private key 생성·비밀 저장소 등록·회전에는 사용자 또는 운영자 개입이 필요하다. 프론트엔드와 API를 같은 상위 사이트 아래에 배포해야 하므로 서로 무관한 호스팅 도메인을 계속 사용하려면 이 결정을 재검토하고 `SameSite=None`, 별도 CSRF token, 제3자 쿠키 제한까지 다뤄야 한다. 엄격한 Origin 검증은 브라우저가 Origin을 보내지 않는 비표준 클라이언트를 거부하므로 Refresh·로그아웃 API를 브라우저 전용 계약으로 취급한다. Path를 `/api/auth`로 제한하면 향후 인증 엔드포인트를 그 밖으로 옮길 때 cookie 계약도 함께 변경해야 한다.

### ADR-031: 현재 기기와 모든 기기 로그아웃 명령 분리

**상태**: Accepted  
**날짜**: 2026-09-15  
**결정**: 로그인할 때 생성한 Refresh Token 패밀리를 하나의 기기 세션으로 취급한다. 일반 로그아웃은 요청에 포함된 Refresh Token이 속한 현재 패밀리만 Redis에서 폐기하고 현재 Refresh 쿠키를 만료시킨다. 별도의 모든 기기 로그아웃 명령은 인증된 사용자의 모든 Refresh Token 패밀리를 Redis에서 폐기하고 현재 Refresh 쿠키도 만료시킨다. 이를 위해 Redis에서 사용자별 활성 패밀리를 조회할 수 있게 유지한다. 두 명령 모두 Access Token denylist를 추가하지 않으므로 이미 발급된 Access Token은 최대 15분 동안 유효할 수 있다. meet-me 서비스 로그아웃은 Google·Kakao 계정 연결, 공급자 Refresh Token이나 Google Calendar grant를 폐기하지 않으며 공급자 연결 해제는 별도 명령으로 둔다.

**이유**: 일상적인 로그아웃으로 사용자의 다른 정상 기기까지 끊지 않으면서, 기기 분실이나 세션 탈취가 의심될 때는 한 번의 명령으로 장기 갱신 권한을 모두 회수할 수 있게 하기 위해서다. 기존 토큰 패밀리 모델을 그대로 기기 세션 경계로 사용하므로 일반 요청마다 Redis를 조회하지 않는 짧은 Access JWT 구조도 유지할 수 있다.

**트레이드오프**: 현재 기기 로그아웃과 모든 기기 로그아웃을 위한 API·UI·권한 테스트가 각각 필요하고 Redis에 사용자별 패밀리 인덱스를 일관되게 유지해야 한다. Access Token을 즉시 폐기하지 않으므로 분실 기기에서 이미 발급된 토큰은 최대 15분간 사용할 수 있지만 요청마다 Redis를 조회하거나 denylist를 관리하는 비용은 피한다. 서비스 로그아웃과 공급자 연결 해제가 분리되어 사용자가 차이를 이해할 수 있는 화면 문구가 필요하다.

### ADR-032: Wanted 제출 MVP를 익명 주최자 모드로 공개

**상태**: Accepted

**날짜**: 2026-09-18
**결정**: Wanted AI Champion 심사·투표용 제출 MVP에서는 Google·Kakao 소셜 로그인과 Google Calendar 연동을 구현·노출하지 않고 모든 사용자가 로그인 없이 핵심 조율 흐름을 체험하게 한다. 방 생성 또는 참여 시 서버가 ADR-020·ADR-021의 브라우저 단위 `Secure HttpOnly` 불투명 자격 증명을 발급하며, 방을 만든 세션은 첫 참여자와 `HOST` 역할을 함께 소유한다. 마감·지연 분석 재요청·후보 확정 같은 주최자 명령은 해당 방을 생성한 세션만 수행한다. 공유 초대 링크만으로 참여자 또는 주최자 권한을 인정하지 않는다. 제출 기간 종료 후 소셜 로그인 모드로 전환하는 작업은 자동 날짜 조건이 아니라 명시적인 배포 설정과 회귀 테스트를 거친다. ADR-003, ADR-009, ADR-019와 ADR-022~ADR-026 및 ADR-029~ADR-031은 Post-MVP 목표로 유지하되 제출 MVP의 실행 범위에서는 이 결정이 우선한다.

**이유**: 심사위원과 투표자가 별도 계정 동의나 로그인 없이 서비스의 핵심인 자연어 조건 수집, 결정론적 일정·장소 매칭과 후보 확정을 즉시 체험하게 하고, 2026-09-21 제출 일정에서 OAuth 검수·Calendar 권한·장기 토큰 구현을 핵심 가치 검증의 선행 조건에서 제거하기 위해서다. 기존 게스트 자격 증명 경계를 방 생성자에게도 적용하면 공유 링크와 주최자 권한을 분리하면서 별도 데모 계정이나 공용 비밀번호를 만들지 않아도 된다.

**트레이드오프**: 쿠키가 삭제되거나 다른 브라우저·기기로 이동하면 주최자 권한을 복구할 수 없고, 공개 기간에는 누구나 새 방을 만들 수 있어 호출 제한·자원 정리·남용 방지가 필요하다. 소셜 계정 기반 복구, 다중 기기 세션, Calendar 자동 불가 시간 수집은 제공하지 않는다. 대신 제출 MVP의 외부 계정·비밀정보와 구현 범위를 줄이고, Post-MVP 인증을 추가할 때 익명 방 소유권을 로그인 계정으로 연결하거나 이전하는 정책을 별도로 설계할 수 있다.

### ADR-033: 제출 MVP 장소 검색에 Kakao Local API 채택

**상태**: Accepted

**날짜**: 2026-09-18

**결정**: 제출 MVP의 국내 장소 키워드 검색·정규화 공급자로 Kakao Local API를 사용한다. 서버는 REST API Key를 outbound Geo Adapter에만 주입하고 Kakao 응답 DTO를 도메인 밖에 격리한다. 공급자는 검색 결과의 좌표와 표시 이름만 제공하며 검색 결과 고유성 판정, 반경 영역, 거리·교집합과 후보 순위 계산은 서버의 결정론적 로직이 담당한다. Kakao 로그인은 제출 MVP에서 활성화하지 않는다.

**이유**: 초기 대상 사용자가 국내 대학생과 사이드 프로젝트 참여자이고 역·국내 장소명 검색이 핵심이므로 국내 POI 검색을 제공하는 Kakao Local API가 제출 MVP에 적합하다. REST 호출 하나와 앱의 REST API Key로 연동할 수 있어 별도 OAuth 동의나 사용자 위치 권한 없이 서버 어댑터를 구현할 수 있다.

**트레이드오프**: 장소 검색 가용성·할당량·약관과 결과 품질이 Kakao에 종속되고 해외 장소 지원과 공급자 교체 비용이 생긴다. REST API Key를 비밀정보로 관리해야 하며 운영 환경의 고정 송신 IP가 확정되기 전에는 IP 제한을 적용하기 어렵다. 이를 완화하기 위해 Geo port와 공급자 DTO를 분리하고 검색 결과 스냅샷과 도메인 판정 결과만 내부 모델로 변환한다.

### ADR-034: 핵심 조율 도메인을 네 Aggregate로 분리

**상태**: Accepted
**날짜**: 2026-09-19
**결정**: 제출 MVP의 핵심 도메인을 `MeetingRoom`, `Participant`, `Submission`, `CoordinationRun` 네 Aggregate로 분리한다. `MeetingRoom`은 방 설정과 입력 수집 종료를, `Participant`는 방별 역할과 익명 세션 소유권을, `Submission`은 참여자별 최신 불변 제출 버전을, `CoordinationRun`은 고정 제출 배치부터 후보와 최종 확정까지를 소유한다. Aggregate를 넘는 원자성은 Application 서비스의 Spring 트랜잭션과 PostgreSQL FK·unique·check 제약으로 보장한다. 소셜 `User`와 공급자 계정은 Post-MVP Aggregate로 남긴다.

**이유**: 참여자와 제출을 모두 방 Aggregate에 포함하면 동시 제출마다 큰 객체를 갱신하고 방 행에 경합이 집중된다. 제출 버전과 조율 시도·후보는 수명주기와 증가 패턴도 서로 다르다. 네 경계로 나누면 도메인 불변식을 각 책임 안에 유지하면서 PostgreSQL 트랜잭션으로 마감·배치·Outbox 같은 다중 Aggregate 작업을 조정할 수 있다.

**트레이드오프**: 한 Aggregate만 저장해 전체 유스케이스를 끝낼 수 없고 Application 조정 코드, 저장소 port와 DB 제약이 늘어난다. 여러 행을 함께 바꾸는 기능은 반드시 명시적 트랜잭션과 동시성 테스트가 필요하다. 대신 대형 Aggregate와 장기 행 잠금을 피하고 이후 인증·Calendar·비동기 처리 경계를 독립적으로 확장할 수 있다.

### ADR-035: DST gap 이동과 overlap 실제 구간 보존

**상태**: Accepted
**날짜**: 2026-09-19
**결정**: ADR-014의 `ZoneRules` 변환을 다음과 같이 구체화한다. DST gap 안의 존재하지 않는 지역 경계 시각은 전환 직후의 다음 유효 시각으로 이동한다. DST overlap 구간은 시작 경계에 더 이른 Instant를 만드는 offset을, 종료 경계에 더 늦은 Instant를 만드는 offset을 선택해 반복된 실제 구간 전체를 보존한다. 결과가 비어 있거나 역전되면 거부한다.

**이유**: 자연어와 주간 반복 조건은 offset 없이 지역 날짜·시간만 제공하므로 overlap에서 사용자에게 offset 선택을 요구할 수 없다. gap을 다음 유효 시각으로 이동하면 존재하지 않는 후보를 만들지 않고, overlap의 양쪽 실제 시간을 포함하면 가능한 시간이나 절대 불가 시간을 조용히 누락하지 않는다.

**트레이드오프**: gap을 포함한 구간은 입력한 벽시계 길이보다 짧아질 수 있고 overlap 구간은 길어질 수 있다. 향후 사용자 선택 시간대를 제공할 때 이 정책을 API 도움말과 화면에 설명해야 한다. 반면 Java 기본 offset 선택에 암묵적으로 의존하지 않고 같은 tzdb에서 결정론적인 결과를 낸다.

### ADR-036: 30일 고정 익명 브라우저 세션과 Origin 방어 채택

**상태**: Accepted
**날짜**: 2026-09-19
**결정**: ADR-020·ADR-021·ADR-032의 제출 MVP 익명 자격 증명을 32바이트 암호학적 난수로 생성하고, 원문은 API 호스트 전용 `Secure HttpOnly; SameSite=Lax; Path=/api` 쿠키로만 전달한다. 쿠키 `Domain`은 지정하지 않고 `Max-Age`와 PostgreSQL 만료 시각은 발급 시점부터 고정 30일로 맞춘다. 서버는 원문 대신 SHA-256 digest와 만료·회수 상태만 저장하며 사용에 따른 수명 연장이나 자동 회전을 제공하지 않는다. 게스트 쿠키로 상태를 변경하는 요청은 정확한 프론트엔드 Origin과 일치해야 하고 Origin 누락·불일치 및 wildcard credential CORS를 거부한다. 별도 CSRF token은 추가하지 않는다. 만료·위조·회수된 쿠키는 새 방 생성·참여에서 새 세션으로 대체할 수 있지만 기존 참여 소유권을 이전하거나 복구하지 않는다.

**이유**: 256비트 원문은 데이터베이스에 SHA-256 digest만 저장해도 오프라인 역산이 현실적으로 불가능하고 별도 digest 비밀키 수명주기를 추가하지 않는다. 고정 30일은 심사·투표와 단기 조율 기간 동안 새로고침과 재방문을 지원하면서 무기한 익명 권한을 피한다. 같은 상위 사이트의 프론트엔드·API 배치, `SameSite=Lax`와 엄격한 Origin 검증을 결합하면 JavaScript에 자격 증명이나 별도 CSRF token을 노출하지 않고 쿠키 기반 변경 요청을 방어할 수 있다.

**트레이드오프**: 자격 증명이 유출되면 만료 또는 서버 회수 전까지 해당 브라우저 세션이 소유한 여러 방에 영향을 줄 수 있고 자동 회전이 이를 줄여 주지 않는다. 쿠키 삭제·만료·기기 변경 시 기존 소유권을 복구할 수 없으며, 엄격한 Origin 검증 때문에 브라우저가 아닌 클라이언트는 상태 변경 API를 사용할 수 없다. 30일 동안 불필요한 익명 세션 행이 남을 수 있어 후속 자원 정리 작업이 필요하다.

### ADR-037: Gemini 3.8 Flash 고정 모델과 경계가 닫힌 조건 유니온 채택

**상태**: Accepted
**날짜**: 2026-09-19
**결정**: 제출 MVP의 자연어 구조화 모델을 stable ID `gemini-3.8-flash`로 고정하고 Google GenAI Java SDK 1.72.0을 사용한다. `latest` alias는 사용하지 않는다. Structured Output은 입력 참조별 최대 32개의 `TIME_WINDOW`, `SPECIFIC_PLACE`, `TRAVEL_CONSTRAINT`, `UNRESOLVED_PLACE` 조건 유니온으로 제한하고 추가 속성과 좌표를 금지한다. 방은 주최자를 포함해 최대 50명, Gemini UTF-8 응답은 최대 256KiB로 제한한다. Phase 5는 장소 표현 분류와 LLM 좌표 거부까지만 담당하고 Kakao 정규화는 Phase 6, Redis Streams 전달은 Phase 8 경계에 둔다.

**이유**: 고정 stable ID와 SDK 버전은 모델 alias 교체에 따른 출력 계약 변화를 방지하고, 닫힌 조건 유니온과 이중 서버 검증은 LLM이 결정론적 매칭 경계나 좌표 판정을 침범하지 못하게 한다. 50명·32조건·256KiB 상한은 제출 MVP의 10,000 코드 포인트 입력 제한과 일치하는 비용·메모리·검증 경계를 제공한다. 실제 공급자 검색과 메시지 전달을 후속 브랜치로 분리하면 각 외부 장애와 데이터 소유권을 독립적으로 테스트할 수 있다.

**트레이드오프**: 모델 교체와 SDK 업그레이드는 명시적인 문서·회귀 평가가 필요하고, 50명을 넘는 대규모 모임은 지원하지 않는다. 경계가 닫힌 스키마는 새로운 조건 타입을 추가할 때 API·저장 형식·프롬프트를 함께 변경해야 한다. Phase 5만 배포하면 Outbox를 Redis로 전달하는 런타임 consumer와 Kakao 좌표 정규화가 아직 없어 전체 후보 생성은 후속 브랜치가 완료될 때까지 동작하지 않는다.

### ADR-038: 보수적 장소 정규화와 플랜별 결정론적 후보·확정 정책

**상태**: Accepted
**날짜**: 2026-09-19

**결정**: Kakao Local 키워드 검색은 Unicode NFKC·공백·대소문자를 정규화한 질의와 장소명이 전체 노출 가능 정확도순 결과에서 정확히 한 건 일치할 때만 장소로 채택한다. 첫 결과를 자동 선택하거나 공급자 신뢰도 점수를 가정하지 않는다. 정규화된 장소 ID·표시명·좌표만 방 수명 동안 PostgreSQL에 저장하고 원본 응답은 보관하지 않는다. 허용 영역 교집합에서는 경계까지의 최소 여유가 가장 큰 결정론적 대표점을 사용하며 실제 매장을 자동 선택하거나 개별 참여자의 장소명을 후보 표시명으로 노출하지 않는다. Plan A, B, C는 종류별 최대 한 카드로 만들고, Plan C 동률은 참석 인원, 공통 가능 총시간, 가장 이른 시작, 정렬된 내부 참여자 식별자 순으로 해소한다. 최소 2명 후보가 없으면 빈 후보 집합과 `NO_MATCH`로 정상 완료한다. 최종 확정은 같은 후보 재요청을 멱등하게 처리하고 다른 후보 경합에서는 먼저 커밋된 선택을 유지한다.

**이유**: Kakao 응답에는 서버가 임계값으로 사용할 수 있는 신뢰도 점수가 없으므로 동명 장소를 임의 선택하지 않아야 한다. 플랜 종류별 카드와 안정적인 동률 규칙은 동일 입력의 결과를 재현하면서 프론트엔드가 제한된 후보 계약을 유지하게 한다. 빈 결과와 외부 장애를 분리하고 첫 확정을 유지하면 사용자가 공유한 결과가 조용히 바뀌지 않는다.

**트레이드오프**: 보수적인 정확명 정책 때문에 사람이 이해할 수 있는 일부 장소도 미확정으로 남을 수 있다. 공통 가능 지역은 실제 매장이 아니므로 주최자가 구체 장소를 별도로 정해야 한다. Plan C 동률에서 일부 가능한 참여자 조합을 숨기며, 첫 확정 우선 정책은 다른 후보로 바꾸려면 향후 명시적 확정 변경 기능이 필요하다. 대신 공급자 오판, 비결정적 후보 순서와 동시 확정 덮어쓰기를 피한다.
